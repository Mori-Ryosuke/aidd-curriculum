# 第1部：提出物

# 社内 備品貸出アプリ 要件定義書

## ■ 目的（なぜ作るか）

総務（実質1名）が備品の所在を電話と口頭で追跡している状態をなくす。

達成したい状態は2つ。

1. **「今、誰が何を借りているか」を全社員が自分で見られる** — 総務に聞きに来るのをやめさせ、借りたい人が本人に直接交渉できるようにする
2. **「いつから借りているか」が見える** — 名前だけ分かっても、1週間前か半年前か分からなければ声をかけるタイミングが判断できない。借りっぱなしを検知可能にする

副次的に、総務の台帳手打ちと催促の声かけを廃止する。

## ■ ユビキタス言語

| 用語 | 定義 |
|---|---|
| **備品品目**（ItemType） | 「プロジェクタ」など備品の種類。名称は正規化済みで、同一物を指す表記は1件に統合する |
| **管理単位**（TrackingMode） | 品目ごとに `個体管理` または `数量管理` のいずれかを持つ |
| **個体管理品目** | 1台ずつ識別する品目。プロジェクタ、ビデオカメラ、貸出用ノートPC |
| **数量管理品目** | 総台数と貸出可能台数のみ管理し、個体を識別しない品目。三脚、延長コード等 |
| **備品個体**（Unit） | 個体管理品目における1台 |
| **管理番号** | 本システムが発行する個体の識別子（`EQ-001`形式）。テプラで印刷して貼付する |
| **資産番号** | 経理が貼付した固定資産の番号。読める個体のみ参考情報として併記する。本システムは資産管理をしない |
| **総台数** | 廃棄済を除く保有台数 |
| **貸出可能台数** | 総台数 −（貸出中＋修理中＋紛失）。**「在庫」という語は使わない** |
| **備品状態** | `利用可能` / `貸出中` / `修理中` / `紛失` / `廃棄済` の5値（`修理中`・`紛失` は第2弾） |
| **貸出**（Loan） | 利用開始日が本日である持ち出し。開始日時はシステムが自動記録する |
| **予約**（Reservation） | 利用開始日が未来日である押さえ。第2弾。UI上に「予約」という語は出さない |
| **返却** | 物理的に戻り、かつシステム上の返却記録が完了した状態。口頭申告は返却ではない |
| **返却予定日** | 利用者が申告する返却の目安。初期値は貸出日の翌営業日。超過しても貸出はブロックしない |
| **延長** | 借用者本人が返却予定日を先送りする操作。回数制限なし |
| **超過** | 返却予定日を過ぎ、かつ未返却の状態 |
| **超過日数** | 返却予定日から本日までの営業日数 |
| **通算貸出日数** | 貸出日から本日までの暦日数。延長を重ねても実態が見えるようにするための指標 |
| **営業日** | 土曜・日曜・日本の祝日を除く日 |
| **利用者** | 全社員（約150人）。社員なら誰でも貸出・返却できる |
| **管理者** | 正規の総務4名（佐藤さんを含む）。備品マスタ管理と超過一覧の閲覧ができる。パート職員は含めない |

## ■ ユーザーストーリー（INVEST点検済み）

| ID | ストーリー | 弾 |
|---|---|---|
| S1 | 利用者として、備品の一覧と貸出可能台数を見たい。会議室に行く前に有無を確認したいから | 1 |
| S2 | 利用者として、誰がいつから借りているかを見たい。総務に聞かず本人に直接借りに行けるから | 1 |
| S3 | 利用者として、個体管理品目を借りた記録を自分で残したい | 1 |
| S4 | 利用者として、数量管理品目を借りた記録を自分で残したい | 1 |
| S5 | 利用者として、返した記録を自分で残したい。総務の手打ちを不要にするため | 1 |
| S6 | 利用者として、まだ使うときに自分で期限を延ばしたい。総務に言いに行きたくないから | 1 |
| S7 | 利用者として、期限が過ぎたら知らせてほしい。借りたこと自体を忘れるから | 1 |
| S8 | 管理者として、超過している貸出を一覧で見たい。声をかける相手とタイミングを判断するため | 1 |
| S9 | 管理者として、備品を登録・編集・廃棄したい。データが無いと全機能が動かないから | 1 |
| S10 | 利用者として、未来の日付を指定して備品を押さえたい。当日行って空振りするのを防ぐため | 2 |
| S11 | 管理者として、備品を「修理中」「紛失」にしたい。貸出可能台数から除きたいから | 2 |
| S12 | 管理者として、返却の代理入力をしたい。記録し忘れた人の分を直すため | 2 |
| S13 | 利用者として、過去の貸出履歴を検索したい。「先月これ誰が使った？」に答えるため | 2 |

**INVESTでの指摘と対応**
- S3/S4を分割：個体管理と数量管理はデータモデルもUIも別物になるため、1ストーリーではSmallを満たさない
- S6/S7を分離：延長は利用者の能動操作、通知はシステムの能動動作。Testableの観点で分けた
- S9は分割不能：S1〜S8すべての前提だが、単体では利用者価値が出ない。Valuableを犠牲にしてでも先に作る必要があると判断
- S11を統合：「修理中」と「紛失」は分割可能だが、実装は状態変更の同一機構なので1ストーリーにまとめた
- S10（予約）を第2弾に隔離：期間の重複判定、取消、no-show時の解放条件など未決事項が多く、Estimableを満たさない

## ■ スコープ（MoSCoW）

### Must（第1弾／9月中旬公開）
- 備品一覧の表示（品目・管理番号・貸出可能台数・状態）
- 借用者名・貸出日時の表示（全社員に公開）
- 個体管理品目の貸出／数量管理品目の貸出
- 返却
- 返却予定日（初期値＝貸出日の翌営業日、利用者が変更可）
- 延長（借用者本人・回数制限なし）
- 超過の色分け、「◯営業日超過」「通算◯日」「延長◯回」の表示
- 管理者向け超過一覧
- 超過翌営業日の本人への自動通知
- 金曜朝の管理者向け週次サマリ（停止可）
- 備品マスタの登録・編集・廃棄（管理単位・管理番号・資産番号の登録を含む）
- Microsoft アカウントによる SSO 認証
- 一般利用者／管理者の2階層権限

### Should（第2弾／10月〜）
- 予約（未来日指定）と、予約が入っている場合の延長ブロック
- 「修理中」「紛失」への状態変更
- 管理者による代理返却
- 貸出履歴の閲覧・検索
- 会社独自の休業日（年末年始・夏季休暇）の登録

### Could（第3弾／時期未定）
- CSV出力
- QRコード／バーコード読み取りによる貸出・返却

### Won't（今回作らない）
| 項目 | 理由 |
|---|---|
| 備品の購買申請・稟議 | 「別の紙のフローがある。混ぜないで」 |
| 経理の固定資産台帳との自動連携 | 資産番号は転記のみ。資産管理は本システムの責務ではない |
| 承認ワークフロー（貸出への上長承認） | 誰の承認も必要と言われていない。画面が増えて利用率が下がる |
| 超過による貸出のブロック | 「ガチガチにすると使われなくなるのが一番怖い」。超過は可視化のみ |
| 延長回数の上限 | 上限を設けると「上限到達者が総務に相談に来る」運用になり、総務の負荷が増える |
| 部署別・役職別の細かい権限 | 「社員なら誰でも。細かく分けると使われなくなる」 |
| 管理者への個別・即時の超過通知 | 「メールが埋まって見なくなる」。週次サマリ1通に集約 |
| 棚卸・減価償却 | 業務範囲外 |
| スマートフォン最適化 | 「社内のパソコンから見られるやつ」 |

## ■ EARS記法による要件

### Ubiquitous（常時）
- THE システムは、すべての品目について管理単位（個体管理／数量管理）を1つ保持しなければならない。
- THE システムは、すべての備品個体について定義済みの状態を1つ保持しなければならない。
- THE システムは、貸出可能台数を「総台数 −（貸出中＋修理中＋紛失）」として算出しなければならない。
- THE システムは、貸出・返却・延長・備品マスタ変更について、操作者と日時を秒精度で記録しなければならない。
- THE システムは、記録済みの貸出履歴を削除する手段を提供してはならない。
- THE システムは、貸出中の備品について、借用者名・貸出日時・返却予定日を全利用者に表示しなければならない。
- THE システムは、営業日を「土曜・日曜・日本の祝日を除く日」として判定しなければならない。

### Event-driven（WHEN）
- WHEN 利用者が貸出を確定したとき、THE システムは 利用者に日時を入力させることなく、確定時のサーバ日時を貸出日時として記録しなければならない。
- WHEN 利用者が貸出画面を開いたとき、THE システムは 返却予定日の初期値として貸出日の翌営業日を設定しなければならない。
- WHEN 利用者が個体管理品目の貸出を確定したとき、THE システムは 当該個体を `貸出中` に変更しなければならない。
- WHEN 利用者が数量管理品目の貸出を確定したとき、THE システムは 貸出可能台数を1減らし、借用者を含む貸出記録を1件作成しなければならない。
- WHEN 利用者が返却を確定したとき、THE システムは 対象を `利用可能` に戻し、返却日時を記録しなければならない。
- WHEN 借用者本人が延長を確定したとき、THE システムは 返却予定日を更新し、延長回数を1増やし、延長の履歴を記録しなければならない。
- WHEN 貸出が超過となった翌営業日を迎えたとき、THE システムは 借用者本人にのみ通知を送信しなければならない。
- WHEN 金曜日の朝を迎えたとき、THE システムは 全管理者に超過件数を含む週次サマリを1通送信しなければならない。
- WHEN 管理者が返却期限の初期日数を変更したとき、THE システムは 以後の新規貸出にその値を適用しなければならない。ただし既存の貸出の返却予定日を変更してはならない。

### Unwanted behaviour（IF-THEN）
- IF 対象個体がすでに `貸出中` であるならば、THEN THE システムは 貸出を拒否し、現在の借用者名と貸出日を表示しなければならない。
- IF 数量管理品目の貸出可能台数が0であるならば、THEN THE システムは 貸出を拒否しなければならない。
- IF 2名が同一個体（または残1台の数量管理品目）の貸出を同時に確定したならば、THEN THE システムは 先に確定した1件のみを成立させ、他方に拒否理由を表示しなければならない。
- IF 対象個体が `修理中`・`紛失`・`廃棄済` であるならば、THEN THE システムは 貸出を拒否しなければならない。
- IF 借用者本人以外の利用者が返却または延長を要求したならば、THEN THE システムは これを拒否しなければならない。
- IF 返却予定日として貸出日より前の日付が指定されたならば、THEN THE システムは これを拒否しなければならない。
- IF 貸出中の個体に対して廃棄が要求されたならば、THEN THE システムは これを拒否し、未返却であることを通知しなければならない。
- IF 一般利用者が備品マスタの変更を要求したならば、THEN THE システムは これを拒否しなければならない。
- IF 認証されていない要求であるならば、THEN THE システムは いかなる貸出・返却・延長・マスタ変更も許可してはならない。
- IF 登録しようとする品目名が既存の品目名と完全一致するならば、THEN THE システムは 重複として登録を拒否しなければならない。
- IF 通知の送信に失敗したならば、THEN THE システムは 貸出データを変更することなく、送信失敗を記録しなければならない。

### State-driven（WHILE）
- WHILE 個体が `貸出中` である間、THE システムは 一覧に借用者名・貸出日時・返却予定日を表示しなければならない。
- WHILE 貸出が超過している間、THE システムは 当該貸出を色分けし、「◯営業日超過」「通算◯日」「延長◯回」を表示しなければならない。
- WHILE 貸出が超過している間、THE システムは 当該貸出を管理者向け超過一覧に表示しなければならない。
- WHILE 利用者が超過中の貸出を保持している間も、THE システムは 当該利用者による他の備品の貸出を妨げてはならない。
- WHILE 個体が `修理中` または `紛失` である間、THE システムは 貸出操作を提供してはならない。（第2弾）

### Optional feature（WHERE）
- WHERE 予約機能が有効な場合、利用者が未来日を利用開始日として指定したとき、THE システムは これを貸出ではなく予約として登録しなければならない。（第2弾）
- WHERE 対象個体に次の予約が存在する場合、IF 借用者が予約開始日を超える延長を要求したならば、THEN THE システムは 延長を拒否し、次の予約者名と開始日を表示しなければならない。（第2弾）
- WHERE 管理者が週次サマリを停止している場合、THE システムは 当該管理者にサマリを送信してはならない。

## ■ 受入条件（Given-When-Then）

### AC-1 個体管理品目の貸出（正常系）
```
Given 品目「プロジェクタ」は個体管理で、個体「EQ-003」が「利用可能」である
  And 利用者「営業部・田中」がMicrosoftアカウントで認証済みである
  And 本日は 2026-09-16（水）である
When 田中が EQ-003 の「借りる」を実行し、日付を変更せず確定する
Then EQ-003 の状態が「貸出中」になる
  And 返却予定日に 2026-09-17（木）が設定される
  And 一覧に「貸出中／田中／9/16 9:12／返却予定 9/17」と表示される
  And 田中は日時を一切入力していない
```

### AC-2 数量管理品目の貸出（正常系）
```
Given 品目「三脚」は数量管理で、総台数5・貸出中2・貸出可能3である
When 田中が「三脚」を借りる
Then 貸出可能台数が2になる
  And 貸出記録が1件作成される
  And 個体番号は記録されない（識別しないため）
```

### AC-3 金曜午後の貸出（境界値・営業日）
```
Given 本日は 2026-09-18（金）である
  And 2026-09-19（土）・20（日）は営業日ではなく、21（月）は営業日である
When 田中が 15:30 に EQ-003 を借り、日付を変更せず確定する
Then 返却予定日に 2026-09-21（月）が設定される（翌暦日の 9/19 ではない）
When 2026-09-21（月）9:00 を迎える
Then EQ-003 は超過と判定されない
  And 田中に通知は送信されない
```

### AC-4 祝日を挟む貸出（境界値）
```
Given 本日は 2026-09-18（金）で、9/21（月）が祝日である
When 田中が EQ-003 を借りる
Then 返却予定日に 2026-09-22（火）が設定される
```

### AC-5 同日午前・午後の連続利用（境界値）
```
Given EQ-003 が「利用可能」である
When 田中が 2026-09-16 09:12 に借り、同日 12:30 に返却し、
     鈴木が同日 13:05 に借りる
Then 履歴に2件の貸出記録が残り、時系列で田中→鈴木の順に並ぶ
  And 貸出日と返却日が同一日でもエラーにならない
```

### AC-6 二重貸出（異常系）
```
Given EQ-003 が「貸出中」（借用者：田中）である
When 鈴木が EQ-003 を借りようとする
Then 貸出は成立しない
  And 「営業部・田中さんが9/16から借用中です」と表示される
```

### AC-7 残1台への同時貸出（境界値・競合）
```
Given 品目「三脚」の貸出可能台数が1である
When 田中と鈴木が同一秒に「借りる」を実行する
Then 貸出記録は1件だけ成立し、貸出可能台数は0になる（-1にならない）
  And 成立しなかった側に拒否メッセージが表示される
```

### AC-8 貸出可能台数ゼロ（境界値）
```
Given 品目「延長コード」は総台数2・貸出中2である
When 田中が一覧を開く
Then 「貸出可能 0／2台」と表示され、「借りる」は実行できない
  And 借りている2名の名前が表示される
```

```

【確定した目的】

副次目的：総務の台帳手打ちと催促の声かけを廃止する。

【確定した用語定義】
- 備品品目(ItemType)：備品の種類。名称は正規化済み、同一物を指す表記は1件に統合
- 管理単位(TrackingMode)：品目ごとに「個体管理」または「数量管理」
- 個体管理品目：プロジェクタ、ビデオカメラ、貸出用ノートPC（1台ずつ識別）
- 数量管理品目：三脚、延長コード等（総台数と貸出可能台数のみ、個体を識別しない）
- 備品個体(Unit)：個体管理品目における1台
- 管理番号：本システムが発行する個体識別子（EQ-001形式）。テプラで印刷・貼付
- 資産番号：経理が貼付した固定資産番号。読める個体のみ参考情報として併記。
  本システムは資産管理をしない
- 総台数：廃棄済を除く保有台数
- 貸出可能台数：総台数 −（貸出中＋修理中＋紛失）。★「在庫」という語は使用禁止
- 備品状態：利用可能／貸出中／修理中／紛失／廃棄済（修理中・紛失は第2弾）
- 貸出(Loan)：利用開始日が本日である持ち出し。開始日時はシステムが自動記録
- 予約(Reservation)：利用開始日が未来日である押さえ。UI上に「予約」の語は出さない
- 返却：物理的に戻り、かつシステム上の返却記録が完了した状態。口頭申告は返却ではない

- 延長：借用者本人が返却予定日を先送りする操作。回数制限なし
- 超過：返却予定日を過ぎ、かつ未返却の状態
- 超過日数：返却予定日から本日までの営業日数
- 通算貸出日数：貸出日から本日までの暦日数
- 営業日：土曜・日曜・日本の祝日を除く日（会社独自の休業日登録は第2弾）
- 利用者：全社員（約150人）。社員なら誰でも貸出・返却できる
- 管理者：正規の総務4名。備品マスタ管理と超過一覧の閲覧。パート職員は含めない

Could（第3弾／時期未定）

Won't（今回作らない）
```
