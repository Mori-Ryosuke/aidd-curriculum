# Ch.1 提出物：社内 備品貸出アプリ（equipment-lending）

作成：情シス担当（受講者役）
顧客：総務部 佐藤さん
基準日：2026年6月1日（月）
ヒアリング：4ラウンド＋画面イメージ確認1ラウンド

---

## ■ 目的（なぜ作るか）

**総務が備品を探し回る時間をゼロにする。**

現状（佐藤さんの証言）：

| 事実 | 数値 |
|---|---|
| 備品を探し回る頻度 | 月2〜3回 |
| 1回あたりの所要 | 30分〜半日（総務3人が動くこともある） |
| 紛失による買い直し | 年1件・2万円（Bluetoothスピーカー） |
| 「返した」と申告されたが現物が無かった事故 | 発生あり（机の下から発見） |
| 役員会議の遅延 | 10分押し（プロジェクタ捜索） |

原因は「借りた記録が無い／あっても信用できない」ことではなく、**誰が持っているかが総務にしか（総務にも）分からない**こと。佐藤さんの言葉では「**探さなくてよくなること。誰が持ってるかがパッと見て分かれば、それでいい。分かれば声かけて戻してもらえる**」。

したがって本システムのゴールは「完璧な備品台帳をつくること」ではなく、**社員が総務に聞かずに自己解決でき、総務が「気づく」のをシステムに肩代わりさせること**とする。この優先順位は、以下すべての設計判断の根拠になっている。

**測定可能なゴール（稼働3か月後）**
- 総務への「◯◯空いてますか」の問い合わせ：月20件以上 → 月5件以下
- 探索に費やす時間：月2〜3回×30分〜半日 → 月1回以下
- 返却予定日超過に総務が気づくまでの日数：不定（記憶頼み） → 翌営業日

## ■ ユビキタス言語（用語定義）

ヒアリング中に解釈が割れた語を定義する。**画面に出す語**と**仕様書内だけで使う語**を分けている。

| 用語 | 定義 | 画面表示 |
|---|---|---|
| **保有台数** | 会社が所有する総数（例：プロジェクタ3台） | ✕ 出さない |
| **空き** | 今この瞬間に借りられる数。＝ 保有台数 −貸出中 −修理中/故障中 −常設 | ○ 「空き 1台」 |
| **貸出中** | 現物が社員の手元にある状態 | ○ |
| **常設** | 会議室等に据え付けで戻らない備品。空きの計算から完全に除外し、置き場所つきで別枠表示 | ○ |
| **修理中／故障中** | 物理的に貸せない状態。空きから除外。**理由をそのまま表示する**（「貸出不可」は理由が分からず総務が説明できないため却下） | ○ |
| **返却予定日** | 借りるときに本人が入力する、返す予定の日 | ○ |
| **返却申告** | 借りた人（または代理の人）が「返しました」を押した状態。**この時点で空きに戻る** | △ 社員には見えない |
| **返却確定** | 総務が現物を目視して確認した状態 | ✕ 総務のみ |
| **未確認** | 返却申告済みだが返却確定していない状態 | ✕ 総務のみ |
| **自動確定** | 返却申告から14日経過し、総務の確認が無いまま自動で確定した状態 | ✕ 総務のみ |
| **予約** | 将来の日付を押さえる行為。**社員の画面にはこの語を一切出さない**（後述） | ✕ 仕様書のみ |
| **代理貸出** | 総務が他の社員の名義で貸出を登録すること | ○ 「代わりに借りる」 |
| **代理返却申告** | 借りた本人以外が返却申告すること | ○ 「頼まれた分を返す」 |

**総務の現場語との対応**：総務は日常的に「空き」と言っている（「プロジェクタ空いてます？」と電話が来る）。よって画面語は「貸出可能数」ではなく「**空き**」を採用した。「常設」は現場では「置きっぱなし」「据え付け」だが、佐藤さんの同意を得て「常設」に統一。

## ■ ユーザーストーリー（INVEST点検済み）

### 借りる人（全社員 約180名／派遣を含む）

| ID | ストーリー | 優先 |
|---|---|---|
| US-1 | **社員**として、**備品の空き数と、貸出中なら誰がいつ返す予定かを一覧で見たい**。総務に電話せず自分で判断するため | Must |
| US-2 | **社員**として、**今すぐ備品を借りたい**。倉庫の前で完結させるため | Must |
| US-3 | **社員**として、**先の日付の分を確保したい**。説明会シーズンに出払って使えない事態を避けるため | Should |
| US-4 | **社員**として、**返却を自分で申告したい**。総務が不在でも記録を残すため | Must |
| US-5 | **社員**として、**他人に頼まれた分の返却を申告したい**。「部長に頼まれて返しに来た」が実際に起きているため | Should |
| US-6 | **社員**として、**自分が今何を借りているかを見たい**。「まだ返してなかったっけ」を自分で解消するため | Must |

### 総務（佐藤さん＋パート1名）

| ID | ストーリー | 優先 |
|---|---|---|
| US-7 | **総務**として、**返却申告された物を倉庫で目視し、まとめて確認済みにしたい**。「返したと言われたが無い」事故を検出するため | Must |
| US-8 | **総務**として、**返却予定日を過ぎている貸出の一覧を見たい**。自分が思い出さなくても気づけるようにするため | Must |
| US-9 | **総務**として、**催促を自分の名前で送りたい**。相手が役員のとき、機械からの通知は角が立つため | Should |
| US-10 | **総務**として、**電話・口頭で頼まれた分を代理で登録したい**。スマホを使わない社員が確実に存在するため | Must |
| US-11 | **総務**として、**備品の登録・状態変更（修理中／常設）・置き場所の編集をしたい**。移転で置き場所が全部変わるため | Must |
| US-12 | **総務**として、**過去の貸出履歴を検索したい**。棚卸しと紛失追跡のため | Must |

**INVEST点検で分割したもの**
- 当初「備品を借りる」を1本にしていたが、**貸出（US-2）と予約（US-3）を分割**。理由：US-2 単独でリリースしても価値が出る（Independent／Valuable）。予約は説明会シーズンにしか効かず、無くても業務は回る。
- 当初「総務が返却を管理する」を1本にしていたが、**現物確認（US-7）と超過督促（US-8/9）を分割**。前者は毎週の定型作業、後者は例外対応で、実装も画面も別。
- US-10（代理貸出）を Should ではなく **Must** にした。理由：「うちの部長とか絶対無理」と明言されており、これが無いと部長の貸出が記録から漏れる。記録が漏れた瞬間、一覧の信頼が崩れて誰も見なくなる（＝目的が達成できない）。

## ■ スコープ（MoSCoW）

### Must（これが無いと目的を達成できない）

- 備品一覧：空き数／貸出中の氏名・部署／返却予定日／置き場所／常設品の別枠表示
- 貸出：返却予定日の入力（デフォルト当日）、備品種別ごとの最長日数チェック
- 同時貸出上限：**1人3点まで**（予約分を含む）
- 返却申告（本人）と、申告時点での空きへの即時反映
- 総務の返却確認（複数選択して一括確定／現物が無い場合の差し戻し）
- 返却予定日超過の一覧（総務のみ）
- 代理貸出（総務が他社員名義で登録。借用者と入力者の両方を記録）
- 備品マスタ管理：登録・廃棄・状態変更（貸出可／修理中／故障中／常設）・置き場所の編集
- 認証：Microsoft 365 アカウントによるシングルサインオン
- 権限：総務ロール／一般社員ロールの2種
- 可視範囲制御：**現在貸出中の氏名は全社員に表示、過去履歴は総務のみ、遅延は本人と総務のみ**
- 同時実行制御：最後の1台を複数人が同時に取ろうとしたときの整合
- 初期データ：稼働前の棚卸し結果を投入（既存Excelからの移行はしない）

### Should（初回リリースに入れたいが、無くても回る）

- 予約（社員画面では「借りる」に統合。当日17:00に自動解放）
- 代理返却申告（頼まれた分を返す）
- 催促（手動送信・定型文つき・佐藤さん名義）
- 未確認の自動確定（14日）と、自動確定だけを絞り込む一覧
- 一覧の並び順：過去90日の貸出件数順
- 新規登録から30日間の「新着」表示（新品が最下部に沈んで存在を知られない問題への対策）
- 代理入力時の氏名インクリメンタルサーチ＋最近入力した人のショートカット

### Could（次の段階）

- Teams への通知連携（催促・返却リマインド）
- QRコード読み取りによる貸出（管理番号シールの貼り替えが前提）
- 棚卸し支援機能
- 貸出実績のレポート（どの備品が足りていないかの購買判断材料）

### Won't（今回はやらない — 明示的に決めた）

| やらないこと | 理由 |
|---|---|
| HDMIケーブル・延長コード等の消耗品管理 | 顧客が「数えていない、諦めた」と明言。管理対象にすると初日から数が合わず、システム全体が信用されなくなる |
| 三脚・台車の管理 | 顧客が「どっちでもいい」。高額品（プロジェクタ／スピーカー／ノートPC／モバイルWi-Fi／ビデオカメラ）に絞る |
| ノートPC以外の個体識別 | 顧客が「番号までは要らない」。ノートPCのみデータ残留の観点で個体を記録 |
| 社外（インターネット）からのアクセス | 顧客が「社内だけでいい、返すのは会社に戻ってから」。公開すると認証・監査の要求水準が跳ね上がる |
| 自動催促 | 顧客の明確な拒否。「役員に機械が催促したら私が呼び出される」 |
| 常設化・廃棄の承認フロー | 顧客が「そこまでやると面倒くさくなる」。総務が単独で操作できる |
| 鍵付きキャビネットの施錠管理 | システムの範囲外。置き場所の説明文に「総務にお声がけください」と記載して回避 |
| 既存Excelデータの移行 | 顧客自身が「今の"貸出中"が本当に貸出中か怪しい」と証言。怪しい初期値を持ち込むと稼働初日から数字が信用されない |
| 過去履歴の全社員公開 | 追跡可能性の観点で総務限定に（後述） |
| 並び順の手動固定 | 顧客が「そこまでは要りません」 |
| 予約時点での個体確保（ノートPC） | 押さえた1台が当日空いていても使えない状態が生じ、苦情になる |

## ■ 非機能要件

### 性能
| 項目 | 要件 | 根拠 |
|---|---|---|
| 一覧表示 | 2秒以内 | 倉庫の前でスマホで開く。遅いと紙に戻る |
| 貸出確定 | 3秒以内 | 朝9時前後に3〜4人が同時に操作 |
| 想定データ量 | 備品60点／社員180名／貸出 月40〜50件（繁忙期 月70〜80件） | ヒアリング実績。**繁忙期は2〜3月と9月** |
| ピーク同時操作 | 5セッション程度（朝9時前後・会議直前） | 同上 |

### 同時実行・整合性
- 最後の1点を複数人が同時に取得しようとした場合、**先に確定した1人のみ成立**。後着には「たった今、他の方が借りていきました」と、次に空く予定日を表示する（無言で失敗させない — 「さっきまで空いてたのに」という苦情を総務に向けさせないため）
- 空きが負の数になってはならない

### 認証・認可
- **Microsoft 365（Entra ID）によるSSO**。独自のID/パスワードは発行しない（パスワードの使い回しを避けるため／顧客も「パスワードがもう1個増えるのは嫌」）
- 権限は2ロール：
  - **総務ロール**：全機能。他人の貸出の編集・返却確定・備品マスタ操作・履歴閲覧
  - **一般ロール**：閲覧、自分の貸出、他人の分の返却申告のみ。**他人の貸出の取消・編集は不可**
- 派遣社員はM365アカウントを保有するため一般ロールで利用可
- **アルバイトのアカウント有無は未確認（情シスへ要確認・未決定事項に記載）**

### ネットワーク
- 社内ネットワークからのみアクセス可能。社外公開しない
- 出張中の返却操作は想定しない（顧客確認済み：「返すのは会社に戻ってから」）

### プライバシー・可視範囲（★ 重要）
| 情報 | 全社員 | 本人 | 総務 |
|---|---|---|---|
| 現在貸出中の氏名・部署 | ○ | ○ | ○ |
| 返却予定日（予定日内） | ○ | ○ | ○ |
| 返却予定日（超過後） | **✕（非表示）** | ○ | ○ |
| 超過日数・遅延の印 | ✕ | ○ | ○ |
| 過去の貸出履歴 | ✕ | 自分の分のみ○ | ○ |

**この設計の理由**：「誰に声をかければいいか分かる」という目的は現在貸出中の氏名だけで達成できる。一方、履歴が全社員に検索可能な状態になると「誰がいつ何を何回借りたか」から出張頻度や在宅勤務の曜日が推測できてしまう。紙の台帳は月次でファイルが分かれ誰も遡らなかったため、これは**システム化によって新しく生じるリスク**である。

### 可用性・運用
- 稼働時間：平日 8:00〜20:00（この時間帯の可用性を重視）
- **半日程度の停止は業務を止めない**（顧客確認済み：紙でしのげる）。したがって冗長構成は不要
- バックアップ：日次
- 一次窓口：**情シス**（総務では対応不可と顧客が明言）
- 監査ログ：貸出・返却・確定・マスタ変更の操作者と日時を記録
- 履歴保持期間：**3年（仮定 — 社内規程を未確認）**

### ユーザビリティ
- スマートフォンのブラウザを主対象（iOS Safari / Android Chrome の現行版）。PCブラウザにも対応
- **社員が覚えるボタンは「借りる」1つ**。「予約する」「押さえる」は画面に出さない
- 総務の操作は「倉庫を見て、あった物にチェックしてボタンを押す。無かったら⚠を押す」の一文で説明できること（パート・新人への引き継ぎが実際に発生する）
- 専用端末（倉庫前のタブレット）は設置しない（顧客の盗難懸念）

### 移行・カットオーバー
- 稼働前の休日に棚卸しを1回実施し、その結果を初期データとする
- **9月のフロア移転とシステム稼働を切り離す**（移転はビル都合で延期の可能性があるため、稼働がそれに引きずられない）。移転時は置き場所の一括更新で対応

## ■ 要件（EARS記法）

異常系の漏れを防ぐため、主要な振る舞いをEARSで記述する。

### 空きの算出
- **WHILE** 備品が修理中・故障中・常設のいずれかである間、システムはその備品を空きに数え**ない**こと
- **WHEN** 社員が備品一覧を開いたとき、システムは備品種別ごとの空き数を表示すること
- **IF** 空きが0である **THEN** システムは空き0を表示し、貸出中の各件について返却予定日を表示すること

### 貸出
- **WHEN** 社員が貸出を確定したとき、システムは返却予定日を必須とし、既定値を当日とすること
- **IF** 指定された返却予定日が備品種別の最長日数を超える **THEN** システムはその日付を選択不可とすること
- **IF** 社員の貸出中および予約の合計が3点である **THEN** システムは4点目の貸出を成立させず、現在借りている3点と総務の連絡先を表示すること
- **IF** 貸出確定の時点で空きが0になっている **THEN** システムは貸出を成立させず、直前に借りた社員の氏名と、次に空く予定日を表示すること
- **WHEN** 貸出用ノートPCの貸出が成立したとき、システムは貸出可能な個体を1台自動で割り当て、その管理番号を表示すること
- **WHEN** 総務が代理貸出を登録したとき、システムは借用者と入力者の双方を記録し、一覧には借用者を表示すること

### 予約（社員画面では「借りる」）
- **WHEN** 社員が当日より後の日付を指定したとき、システムはこれを予約として記録し、その時点では空きを減らさないこと
- **IF** 指定日が本日から1か月を超える **THEN** システムはその日付を選択不可とすること
- **WHEN** 予約日の17:00に至り、当該予約が貸出に切り替わっていない場合、システムは予約を解放すること
- **WHEN** 社員が自分の予約を取り消したとき、システムは即座に解放すること
- 貸出用ノートPCの予約について、システムは予約時点では個体を確保**しない**こと

### 返却
- **WHEN** 返却申告が行われたとき、システムは即時に空きを1増やし、当該貸出を未確認として記録すること
- **WHEN** 借用者以外が返却申告したとき、システムは申告者を借用者とは別に記録すること
- **WHEN** 総務が返却確認を行ったとき、システムは当該貸出を返却確定とすること
- **WHEN** 総務が「現物が無い」を選択したとき、システムは当該貸出を貸出中に戻し、返却予定日超過の対象に含めること
- **WHEN** 返却申告から14日が経過し返却確定されていない場合、システムは自動確定とし、自動確定であることを記録すること
- **WHEN** 総務が確認待ち一覧を絞り込むとき、システムは自動確定のみを抽出できること

### 超過・催促
- **IF** 貸出の返却予定日を過ぎている **THEN** システムは総務の画面に超過日数とともに表示すること
- **IF** 貸出の返却予定日を過ぎている **THEN** システムは借用者本人の画面に超過の表示を行い、**他の社員の画面には返却予定日を表示しないこと**
- **WHEN** 総務が催促を送信したとき、システムは総務担当者の名義で定型文を送信し、送信日時を記録すること
- システムは催促を自動送信**しない**こと

### 権限
- **IF** 一般ロールの社員が他人の貸出の編集・取消を試みる **THEN** システムはこれを拒否すること
- **IF** 一般ロールの社員が履歴の検索を試みる **THEN** システムは自分が借用者である記録のみを返すこと
- **IF** 借用者が退職・異動している **THEN** システムは貸出記録の氏名を保持し続けること

## ■ 受入条件（Given-When-Then／具体例つき）

基準日：2026/6/1（月）。プロジェクタ 保有3台（うち1台は営業部大会議室に常設、1台は修理中）。

### AC-1 空きの算出（正常系）
- **Given** プロジェクタの保有台数が3台、うち1台が常設、1台が修理中、0台が貸出中
- **When** 社員が一覧を開く
- **Then** プロジェクタの空きは **1台** と表示される
- **And** 「修理中 1台」と表示される
- **And** 常設の1台は一覧の「常設品」の枠に、置き場所「営業部 大会議室」つきで表示される

### AC-2 空きの算出（境界値：全台が貸出不可）
- **Given** プロジェクタ3台が、常設1・修理中1・貸出中1
- **When** 社員が一覧を開く
- **Then** 空きは **0台** と表示され、負の数にはならない

### AC-3 貸出（正常系）
- **Given** 山田さん（営業部）が現在0点借りており、プロジェクタの空きが1台
- **When** 6/1に「借りる」→「今日」→返却予定日 6/1 を選んで確定する
- **Then** 貸出が成立し、プロジェクタの空きが0になる
- **And** 一覧に「貸出中 山田(営業部) 6/1(月) 返却予定」と表示される
- **And** 完了画面に置き場所「3階 倉庫」が表示される

### AC-4 返却予定日の上限（境界値）
- **Given** 6/1(月) にプロジェクタ（最長4日）を借りようとしている
- **When** 返却予定日の選択肢を開く
- **Then** 6/1〜**6/4(木)** が選択でき、**6/5(金) 以降は選択できない**
- **補足**：金曜に借りて土日をまたぎ月曜に返す運用（採用説明会）が成立すること — 6/5(金)に借りた場合、6/8(月)が選択できる

### AC-5 種別ごとの最長日数（境界値）
| 備品 | 最長 | 6/1に借りた場合の最終選択可能日 |
|---|---|---|
| プロジェクタ／スピーカー／ビデオカメラ | 4日 | 6/4(木) |
| モバイルWi-Fi | 14日 | 6/14(日) |
| 貸出用ノートPC | 60日 | 7/30(木) |

### AC-6 同時貸出上限（境界値・異常系）
- **Given** 田中さんがプロジェクタ・スピーカー・ノートPCの3点を借りている
- **When** 4点目としてビデオカメラを借りようとする
- **Then** 貸出は成立せず、「同時に借りられるのは3点までです」と、現在借りている3点の名称、総務の内線番号が表示される
- **Given'** 田中さんが2点を借りており、さらに来週の分を1点予約している
- **When** 4点目を借りようとする
- **Then** 予約を含めて3点に達しているため、成立しない

### AC-7 同時実行の競合（異常系）
- **Given** プロジェクタの空きが1台。山田さんと佐々木さんが同時に貸出を確定した
- **When** 佐々木さんの処理が先に確定した
- **Then** 佐々木さんの貸出のみ成立する
- **And** 山田さんには「すみません、たった今 佐々木さん(営業部) が借りていきました」と表示される
- **And** 次に空く予定日（佐々木さんの返却予定日）が表示され、その日から借りる導線が示される
- **And** 空きは0であって、−1にはならない

### AC-8 予約（正常系・社員には「予約」と見せない）
- **Given** 6/1(月)、社員が「借りる」を押し「別の日 6/8(月)」を選択した
- **When** 確定する
- **Then** 「6/8(月) から借ります」と表示される（「予約」「押さえる」の語は画面に出ない）
- **And** 6/1時点の空きは減らない

### AC-9 予約の自動解放（境界値）
- **Given** 6/8(月) に予約があり、当日17:00 時点で貸出に切り替わっていない
- **When** 6/8 17:00 になる
- **Then** 予約は解放され、その備品は他の社員が借りられる状態になる
- **And** 予約者の「3点」のカウントから外れる

### AC-10 予約の上限（境界値）
- **Given** 本日が6/1(月)
- **When** 日付を選択する
- **Then** **7/1(水) までが選択でき、7/2 以降は選択できない**

### AC-11 返却申告と即時反映（正常系）
- **Given** 山田さんがプロジェクタを借りており、空きは0
- **When** 山田さんが「返す」を押す
- **Then** **その場で空きが1になる**（総務の確認を待たない）
- **And** 総務の「返却の確認待ち」に1件追加される
- **And** 一覧から山田さんの名前が消える

### AC-12 代理返却（正常系）
- **Given** 山田部長がプロジェクタを借りている
- **When** 鈴木さんが「頼まれた分を返す」から山田部長のプロジェクタを選び、返却申告する
- **Then** 返却申告が成立する
- **And** 記録には「借用者：山田部長／返却申告者：鈴木」と両方が残る

### AC-13 現物が無かった場合（異常系 — 実際に起きた事故の再現）
- **Given** 加藤さんが5/28にノートPC PC-002 の返却を申告し、未確認のまま
- **When** 総務が倉庫を確認し、PC-002 が無いため「現物が無い」を選ぶ
- **Then** 確認ダイアログに「加藤さんは返したと申告していますが、現物がありません。貸出中に戻して加藤さんに確認しますか？」と表示される
- **And** 確定すると当該貸出は**貸出中に戻り**、空きが1減る
- **And** 返却予定日を過ぎていれば、超過一覧に表示され催促の対象になる
- **And** 「誰が返したと申告したか」が記録に残っており、確認すべき相手が一意に定まる

### AC-14 未確認の自動確定（境界値）
- **Given** 6/1 に返却申告された未確認の貸出がある
- **When** 6/14（13日後）になる → **Then** まだ確認待ちに残っている
- **When** 6/15（14日後）になる → **Then** 自動確定となり、確認待ちから消える
- **And** 履歴には「6/15 自動確定（未確認）」と記録される
- **And** 総務は「自動確定のみ」で絞り込んで一覧できる

### AC-15 遅延情報の可視範囲（★ 異常系・プライバシー）
- **Given** 佐々木さんがプロジェクタを借り、返却予定日は 6/1。本日は 6/5
- **When** **他の社員**が一覧を開く
- **Then** 「貸出中 佐々木(営業部)」と表示される
- **And** **返却予定日は表示されない**（「6/1返却予定」とは出ない）
- **And** 遅延の印・超過日数は表示されない
- **When** **佐々木さん本人**が「自分の分」を開く
- **Then** 「6/1(月) までに返却 ⚠ 4日過ぎています」と表示される
- **When** **総務**が画面を開く
- **Then** 「プロジェクタ 佐々木(営業部) 6/1予定 4日超」と表示され、「催促する」ボタンが押せる

### AC-16 予定日内は日付が見える（AC-15の対照）
- **Given** 佐々木さんの返却予定日が 6/8、本日は 6/5
- **When** 他の社員が一覧を開く
- **Then** 「貸出中 佐々木(営業部) 6/8(月) 返却予定」と**日付が表示される**（待つか他を当たるかを自分で判断できる）

- **When** 「催促する」を押す
- **Then** 佐藤さんの名義の定型文が編集可能な状態で表示される
- **And** 「送る」を押すまで何も送信されない
- **And** システムが自動で催促を送ることはない

### AC-18 権限（異常系）
- **Given** 一般ロールの山田さんがログインしている
- **When** 佐々木さんの貸出記録を編集・取消しようとする
- **Then** 拒否される
- **When** 履歴を検索する
- **Then** 自分が借用者である記録のみが返る（他人の履歴は0件）

### AC-19 退職者（異常系）
- **Given** 退職した伊藤さんがモバイルWi-Fiを借りたままになっている
- **When** 総務が超過一覧を開く
- **Then** 「伊藤（退職）」として氏名が残ったまま表示される（誰だったか追跡できる）

- **Given** ノートPC 5台のうち PC-001 が貸出中、PC-002 が修理中、PC-003〜005 が貸出可

## ■ 整合チェックの結果

要件同士の矛盾を洗い、以下を修正・確定した。

| # | 矛盾していた点 | どう解決したか |
|---|---|---|
| 1 | 「遅延は本人にしか見せない」×「返却予定日を全社員に表示」 → **引き算すれば遅延が分かる** | 予定日を過ぎたら他社員の画面から日付を消す（AC-15/16）。**この矛盾は画面イメージを見せた時に顧客が発見した** |
| 2 | 「社員が押すボタンは"借りる"だけ」×エラー画面のボタンが「押さえる」 | 全画面で「借りる」に統一。「予約」「押さえる」を社員向け画面から排除 |
| 3 | 「1人3点まで」×「予約」 → 予約が上限に含まれるか未定義 | 予約を含めて3点と確定（AC-6） |
| 4 | 「ノートPCは個体を記録」×「予約」 → 予約時に個体を確保するか未定義 | 予約時は確保せず、当日割り当てと確定（AC-20／Won't） |
| 5 | 「返却申告で即座に空きへ戻す」×「総務が現物確認する」 | 空きは申告で戻し、確認は非同期。未確認は14日で自動確定（AC-11/14） |
| 6 | 「初期データは9月の移転時の棚卸しで作る」×「移転が延期される可能性」 → **稼働が移転人質になる** | 棚卸しを移転から切り離し、稼働前の休日に独立して実施 |
| 7 | 「空き＝保有−貸出中」×「据え付けで2年戻らない備品」 | 状態に「常設」を追加し、空きの母数から除外 |
| 8 | 「修理中を貸せない」×Excelの数量は3のまま | 状態を備品1点ごとに持たせ、空きの計算に反映 |
| 9 | 「置き場所は不要」（初回回答）×「倉庫から〜」の固定文言 | 顧客が画面を見て前言撤回。備品ごとの項目に変更（AC-21） |
| 10 | 「よく借りられる順」×「新品は借用実績0で最下部」 → **新品の存在が知られない**（実例あり） | 登録30日以内は「NEW」表示で上位に出す |

### 顧客が言い切ったが、押し返して変えたもの

| 顧客の当初の言 | 最終的にどうしたか | 押し返した理由 |

| 「簡単なやつでいい」「貸出と返却ができれば」 | 空き数の可視化・状態管理・超過検知まで含めた | 「貸出と返却の記録」だけでは、今の Excel と同じで**探す時間が減らない**（＝目的が達成されない） |

### 顧客の判断を優先し、こちらの推奨を引っ込めたもの

| 論点 | こちらの案 | 採用 | 理由 |
|---|---|---|---|

### 私（AI）が出した案のうち、自分で捨てたもの

| 捨てた案 | 理由 |
|---|---|
| 返却は「総務の現物確認をもって確定、それまで空きに戻さない」 | 総務不在の夕方に借りられなくなり、今より不便になる。顧客も「絶対クレームが来る」と即答 |
| 「借りる」と「予約する」のボタンを並べる | 顧客が「どっち押せばいいか分からなくなる」と指摘。日付を聞いて裏で振り分ける形に変更 |
| 総務画面に「確認済みにする」「戻っていない」の2ボタンを並置 | 顧客が「どちらを押すのか分からない、パートさんはもっと分からない」と指摘。主操作を1つに絞り、例外は行内に格納 |
| 「返却時期を確認中」という表示文言 | 顧客が「総務が何か確認しているように見えて、問い合わせが来る」と指摘。**「返却時期 未定」**に変更 |
| 備品の状態を3つ（貸出可／貸出中／貸出不可）で足りるとした | 2年間戻らない据え付け備品が実在。「常設」を追加 |
| 「貸出不可」という状態名 | 理由が分からず総務が説明できない。「修理中」「故障中」と理由をそのまま表示 |

### AIの出力をそのまま採用したもの（正直な申告）

- EARS記法への書き換えと、AC の Given-When-Then への整形は、AIの出力をほぼそのまま使った。ただし**AC-15（遅延の可視範囲）と AC-6（予約を上限に含む）は、AIの初回出力には無かった**。顧客との対話と整合チェックで後から足している。
- 性能要件の数値（一覧2秒・貸出3秒）は一般的な目安をそのまま採用しており、**この職場で検証したものではない**。
