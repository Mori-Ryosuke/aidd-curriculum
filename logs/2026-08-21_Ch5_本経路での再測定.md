# Ch.5 本経路での再測定（`ch4-app/` を実在させた状態）

対象：`.claude/agents/security-audit-officer.md`
位置づけ：[全章 判定ブレ削減 総括](./2026-08-20_全章_判定ブレ削減_総括.md) の「残っている未検証」への対応

---

## なぜ測るか

判定ブレ削減の作業（2026-08-19〜20）で Ch.5 の収束は確認したが、そのとき
**`ch4-app/` はリポジトリに存在しなかった**。つまり測れていたのは
「コードが無いときのフォールバック経路」だけで、**本来の経路
（実コードを読んで採点する）は一度も測っていなかった。**

[Ch.4 実装報告モードの同一性測定](./2026-08-20_Ch4_実装報告モードの同一性測定.md) で
生成物が手に入ったので、その F を `ch4-app/` に据えて測り直した。

---

## 測り方

- `ch4-app/` に Ch.4 の生成物（F）を配置
- フォールバック経路の測定（Y/Z）で使ったのと**同一の点検結果**を、
  毎回新しいインスタンス2つに渡す
- 比較の観点は2つ
  1. 2インスタンス間で一致するか
  2. **フォールバック経路の結果と変わるか**

## 1回目（G/H）：7観点は一致、〈修正計画の現実性〉だけ割れた

| 観点 | G | H |
|---|---|---|
| 判定の正確さ | 一部 | 一部 |
| エビデンスの具体性 | 一部 | 一部 |
| API直叩きの観点 | 達成 | 達成 |
| 監査ログの認識 | 一部 | 一部 |
| リスクの序列 | 一部 | 一部 |
| **修正計画の現実性** | **達成** | **一部** |
| 通し振り返り | 達成 | 達成 |
| 前章の未決定の解消 | 一部 | 一部 |
| 項目 | 9項目中 ○6 ／ △1 ／ 誤り2 | 同左 |

**フォールバック経路（Y/Z）とも一致していた。** 経路の違いで判定は変わらない。
両インスタンスとも実コードを読み（ツール使用5〜6回）、
`where: { id }` に `userId` 照合が無いことを実物から引用していた。

割れたのは〈修正計画の現実性〉。条件に照らすと **H が正しい**。
提出物の Phase 3 には後回しの理由があるが、**Phase 2 には無い**
（「B-1：〜を追加」「D-2：〜を追加」だけ）。

### 原因

条件をこう書いていた。

> **Phase 1 / 2 / 3 のうち、1件以上ある Phase の数** ＋ 後回しの理由の有無
> 達成＝3（かつ Phase 2・3 に理由あり）

**数える対象は Phase の数なのに、理由の有無を括弧書きの付帯条件にしていた。**
付帯のほうが読み飛ばされる。Ch.6 の〈回帰の検出〉とまったく同じ失敗。

## 2回目：2項目のカウントに変えたが、まだ割れた

〈回帰の検出〉と同じ形にして、2項目を数えさせた。

> (1) Phase 1 / 2 / 3 のすべてに1件以上あるか
> (2) 後回しにした Phase 2・Phase 3 の各項目に、後回しの理由が書かれているか
> ★Phase 3 だけに理由があり Phase 2 に理由が無い場合は (2) を満たさない

誤例まで書いたが、**片方のインスタンスがまた「Phase 3 に理由あり」を根拠に達成とした。**

### 原因

(2) が **「理由があるか」という真偽値の判断**のままだった。
数える形になっていないので、「どこかに理由があれば満たす」と読める余地が残る。

## 3回目（K/L）：件数を数えさせて一致

(2) を**件数の比較**に変えた。

> 手順ア：Phase 2 と Phase 3 に並んでいる項目を1件ずつ数える（X）
> 手順イ：そのうち後回しの理由が添えられている項目を数える（Y）
> 手順ウ：**Y ＝ X なら満たす。Y < X なら満たさない。**
> 例：Phase 2 が2件・Phase 3 が2件 → X＝4。Phase 3 の2件にだけ理由 → Y＝2。
> 　　Y(2) < X(4) なので満たさない → 合計「1」＝一部
> ★数えた X と Y をスコア表の「数えた結果」欄に書くこと

| 観点 | K | L |
|---|---|---|
| 判定の正確さ | 一部 | 一部 |
| エビデンスの具体性 | 一部 | 一部 |
| API直叩きの観点 | 達成 | 達成 |
| 監査ログの認識 | 一部 | 一部 |
| リスクの序列 | 一部 | 一部 |
| 修正計画の現実性 | **一部** | **一部** |
| 通し振り返り | 達成 | 達成 |
| 前章の未決定の解消 | 一部 | 一部 |
| 項目 | 9項目中 ○6 ／ △1 ／ 誤り2 | 同左 |

項目別も9つとも一致（A-3・D-1 が誤り、C-1 が△）。
K は判断過程まで書いていた：「(1) Phase 1/2/3 すべて埋まっている＝○／
(2) Phase 2 の2件に後回し理由が無い＝× → 1」。

## 結論

1. **本経路とフォールバック経路で、判定は変わらない。**
   実コードを読んでも、読まずに提出物の記述だけで採点しても、
   8観点・9項目とも同じ結果になった。Ch.5 の採点は経路に依存しない
2. **`ch4-app/` に限定するルールは正しく働いた。**
   全インスタンスが `ch4-app/` 配下だけを読み、
   `equipment-lending/`（過去の通しリハーサルの成果物）には触れていない
3. 残っていた1観点も、**件数を数える形**にして解消した

---

## 得られた教訓

**真偽値の判断を条件に残さない。「数えれば決まる」形にする。**

Ch.5 の初回改修で「まず数える → その数で決まる」表に置き換えたとき、
この1観点だけ**付帯条件を括弧書きで残していた**。それが最後まで揺れた。

段階を追うと、

| 書き方 | 結果 |
|---|---|
| 「Phase の数」＋括弧書きで「かつ理由あり」 | 割れる（G/H） |
| 「2項目のうち書けている数」＋誤例 | まだ割れる |
| 「X 件中 Y 件に理由がある。Y＝X か」 | 一致（K/L） |

**「あるか／ないか」は人によって境界が動く。「何件中何件か」は動かない。**
