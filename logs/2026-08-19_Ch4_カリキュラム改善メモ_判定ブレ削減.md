## この章に固有の発見（最重要）

### 評価が、ワーキングツリーに何があるかで変わっていた

Ch.4 のエージェントは他章と違い **Read / Glob / Bash を持っている**（実装役としてコードを生成するため）。
そのため評価モードでも**リポジトリを自由に読みに行く**。

1回目の測定で、2つのインスタンスとも
`/Users/r-mori/Desktop/aidd-curriculum/equipment-lending/` 配下を点検対象にした。
これは**過去の通しリハーサル（2026-08-17〜18）で生成された別の実装**であり、
教材が定義している `ch4-app/` ではない。

結果：

- 教材の欠陥リストが定義するパス（`app/api/lendings/route.ts` など）で書いた検査結果が
  **「存在しないパス」と判定**され、〈エビデンスの具体性〉が減点された
- 欠陥リストに無い実装（個体管理パスの二重貸出、予約APIのDELETE無認証など）を
  **独自の欠陥として採点根拠にした**
- ツール使用は S=22回、T=18回

**同じ検査結果でも、受講者の作業ツリーに何が残っているかで判定が変わる。**
他章は提出テキストだけを読むので、この穴は Ch.4 だけのもの。

### 対処

- **点検対象を `ch4-app/` だけに限定**。`equipment-lending/` など過去の成果物を読まない
- **`ch4-app/` が存在しない場合はコードを探しに行かない**。検査結果の記述と欠陥リストの定義だけで判定
- エビデンスのパスは「**欠陥リストの定義と一致するか**」で見る。実在確認をしに行かない
- パスの表記揺れだけで △ に落とさない（欠陥の中身が定義と一致していれば ○）

対処後、ツール使用は U=1回、V=1回に落ち、両者とも `ch4-app/` 前提で判定した。

## 他章と共通の改修

1. **7観点の順序を固定**。★評価モードが「下記6観点」でルーブリック表が7観点、という不具合が
   **Ch.2・Ch.3・Ch.4 の3章連続**で見つかった。同じ雛形由来。Ch.5・Ch.6 も要確認
2. **判定語の定義**と、観点を欠陥の判定に連動させる（判断面を二重にしない）
3. **`5個中 ○M ／ △N ／ 未検出K` の表記固定**（小数禁止）
4. **指摘・ヒントを出す順番を固定**（欠陥1→5の順、一度に最大2つ）
5. **到達点に無い基準で判定を動かさない**
6. **推定で判定しない**（提出物の記述だけで判定。「たぶん分かっている」で ○ にしない）

## Ch.4 固有の改修

7. **5つの欠陥それぞれに `受講者の検出判定`（○／△／未検出）を定義**。特に △ の線引きを具体化：
   - 欠陥1：UIとAPIを区別できていれば ○。「在庫チェックが不十分」だけなら △
   - 欠陥3：「認証はあるが認可が無い」と書ければ ○。「権限が甘い」だけなら △
   - 欠陥5：**要件外であること**に触れれば ○。予約APIの認証漏れだけを指摘したら △
     （コードの不具合としては見ているが、スコープ逸脱として見ていない）
8. **「正しい逸脱」の分岐を廃止**。従来は「設計に enum の指定が無い場合は別の逸脱を1つ作る」と
   書かれており、**受講者ごとに検出対象が変わる**構造だった。
   常に「role を String にして理由を残さない」1つに固定
9. **`実装役が持っている事実` を新設**。かかった時間／参照したもの／テストの本数／
   テストを実行したか／型チェック／性能測定／在庫の計算方法／ログ／認証の作り／
   なぜ予約を作ったか／設計との差分。
   ★「実行しましたか」→「はい、通ってます」と答え、**具体的に問い詰められて初めて**
   「書いただけで実行してない」と認める、という段階まで固定した（従来は毎回即興）

## 測定の推移（同一の検査結果を、毎回新しいインスタンス2つに渡す）

### 1回目（S/T）：6/7観点は一致、ただし採点根拠が別のコードだった

| 観点 | S | T |
|---|---|---|
| 欠陥の検出数 | 一部 | 一部 |
| 要件との突き合わせ | 一部 | 一部 |
| 判定の妥当性 | 達成 | 達成 |
| エビデンスの具体性 | **未達** | **一部** |
| スコープ逸脱の検知 | 未達 | 未達 |
| 指示資産への還元 | 一部 | 一部 |
| 前章の未決定の解消 | 未達 | 未達 |
| 欠陥の検出 | 5個中 3.5個 | 5個中 3.5個 |

- 表記が両方とも小数（「3.5個」）。【サマリ】節の指定だけでは効かなかった
- **一致して見えるのは、`equipment-lending/` がディスク上に固定されていたから**。
  作業ツリーが違えば根拠ごと変わる（＝偶然の一致）

### 2回目（U/V）：完全一致

| 観点 | U | V |
|---|---|---|
| 欠陥の検出数 | 一部 | 一部 |
| 要件との突き合わせ | 一部 | 一部 |
| 判定の妥当性 | 達成 | 達成 |
| エビデンスの具体性 | 一部 | 一部 |
| スコープ逸脱の検知 | 未達 | 未達 |
| 指示資産への還元 | 一部 | 一部 |
| 前章の未決定の解消 | 一部 | 一部 |
| 欠陥の検出 | 5個中 ○3 ／ △1 ／ 未検出1 | 5個中 ○3 ／ △1 ／ 未検出1 |
| 欠陥の内訳 | 1○ 2△ 3○ 4○ 5未検出 | 1○ 2△ 3○ 4○ 5未検出 |
| 正しい逸脱 | 未検出 | 未検出 |

意図した基準とも一致（○3 → 欠陥検出=一部／欠陥5未検出 → スコープ逸脱=未達／
「実装後は気をつけて確認する」→ 指示資産=一部／8件素通り → 前章未決定=一部）。

なお 前章の未決定の解消 は S/T が「未達」、U/V が「一部」。
条件（1件でも素通りなら一部）に照らすと U/V が正しい。
