# Ch.4 実装報告モードの同一性測定

実施日：2026-08-20
対象：`.claude/agents/code-inspection-reviewer.md` の**実装報告モード**
位置づけ：[全章 判定ブレ削減 総括](./2026-08-20_全章_判定ブレ削減_総括.md) の「残っている未検証(1)」への対応

---

## なぜ測るか

判定ブレ削減の作業（2026-08-19〜20）で全6章の**評価モード**は収束を確認したが、
Ch.4 の**実装報告モード**は測っていなかった。

この章のエージェントは、受講者が「実装して」と言うと**実際に動くコードを `ch4-app/` に生成する**。
そこに5つの欠陥を仕込み、一方で「必ず正しく実装するもの」は正しく作り、
「絶対に入れないもの」は入れない——という固定仕様がある。

**Ch.5 と Ch.6 の採点は、この生成物に依存する。**
生成が回ごとに違えば、後続2章の点検対象そのものが変わってしまう。

---

## 測り方

同じ依頼（Ch.1〜3 の引き継ぎブロック ＋「実装をお願いします」）を、
**新しいインスタンスに2回**投げ、生成物を突き合わせた。
1回目の出力は scratchpad に退避してから2回目を回している（同じパスに生成するため）。

照合したのは、固定仕様に書かれている14項目。

**結論：演習として採点される面は安定している。**

### 実際のコード（両方に共通して現れた形）

貸出API。在庫を数えるが**0判定をしていない**。数えてから作るまでが分離している。

```ts
const activeCount = await prisma.lending.count({
  where: { equipmentId: body.equipmentId, returnedAt: null },
});
const stock = equipment.totalCount - activeCount;

const lending = await prisma.lending.create({
  data: { userId: session.userId, equipmentId: body.equipmentId, dueDate: new Date(body.dueDate) },
});
```

返却API。**401はあるが `userId` の照合が無い**（認証はあるが認可が無い）。

```ts
const session = await getSession();
if (!session) return NextResponse.json({ error: 'ログインしてください' }, { status: 401 });

const lending = await prisma.lending.update({
  where: { id: params.id },
  data: { returnedAt: new Date() },
});
```

予約API。`getSession()` は呼ぶが **null チェックをせず非null断定**。

```ts
const session = await getSession();
const reservation = await prisma.reservation.create({
  data: { userId: session!.userId, ... },
});
```

## 見つかった差分：仕様が規定していない3点

固定仕様に書かれていない部分で3つ違いが出た。**どれも Ch.5 の点検対象を動かす。**

| # | 箇所 | A | B | Ch.5 への影響 |
|---|---|---|---|---|
| 1 | 予約API の GET | `where: { userId }` で自分の分だけ | **全件返す**（他人の予約が誰でも読める） | C-2「権限のない者が個人情報を閲覧できないこと」のエビデンスが変わる |
| 2 | 返却APIの二重返却チェック | 409 を返す | 無し（上書きして200） | B-1（入力検証）の判定材料が変わる |
| 3 | `GET /api/lendings`（自分の貸出一覧） | 無い（画面で直接取得） | **ある** | Ch.5 は「実装された全API」が点検対象。**API の本数そのものが変わる** |

補助ファイルの構成にも差はあった（A は `lib/stock.ts` に在庫算出を切り出し、B はインライン）。
ただし固定仕様が「動かすために必要なファイルは足してよい」と明記している範囲なので、これは許容。

上の3点は、その許容範囲を超える。**セキュリティ面の実装が変わっている**ため。

### 対処：固定仕様に3点追記

`実装の細部で固定するもの` を新設し、次を明記した。

1. **予約APIの GET は全件を返す**（`where` を付けない）。
   要件外の機能ほど検証が甘い、という欠陥5の性質を閲覧範囲でも成立させるため
2. **返却APIに二重返却チェックを入れない**（409 を返さない）。
   入れると B-1 のエビデンスが変わり、欠陥3だけを見てほしい箇所に別の正しい実装が混ざる
3. **貸出APIに GET を実装しない**。「自分の貸出一覧」は画面から直接 Prisma で取る

あわせてファイル構成の節に「**API ルートは5本だけ。増やさない**」を明記した。

## 再測定（3回目 C）：追記が守られなかった

追記後に生成した C は、**3点のうち2点を守らなかった**。

| 固定した点 | C |
|---|---|
| 予約API GET は全件 | ✗ `where: { userId }` で自分の分だけ |
| 返却APIに二重返却チェックを入れない | ✗ 400 で弾いていた |
| 貸出APIに GET を作らない | ✓ |

さらに A/B に無かった逸脱が出た。貸出APIに **`if (equipment.totalCount <= 0) return 400`**
という**機能しない偽の在庫チェック**（実際の残数ではなく保有数を見ている）。
弾けないので欠陥1は成立しているが、受講者には「在庫チェックがある」ように見える。

### 原因

実装報告モードの `振る舞い` は、**従うべきブロックを列挙**している。

> 末尾の「仕込む欠陥リスト」の欠陥を5つとも必ず含める／
> 「必ず正しく実装するもの」「絶対に入れないもの」も厳守する

新設した `実装の細部で固定するもの` が**この列挙に入っていなかった**ため、
拘束力のあるブロックとして扱われなかった。

### 対処（3点）

1. 振る舞いの列挙に `実装の細部で固定するもの` を追加（従うべきブロックを2つ→3つに）
2. 「生成後に3ブロックと欠陥リストを1項目ずつ読み直して突き合わせてから報告する」を明記
3. **欠陥1の項目の中に**「貸出APIに在庫を理由に弾く if 文を1つも書かない」を誤例つきで明記

## 4回目（D）：2/3 まで改善、返却APIだけ残る

| 固定した点 | D |
|---|---|
| 予約API GET は全件 | ✓ |
| 返却APIに二重返却チェックを入れない | ✗ 409 で弾いていた |
| 貸出APIに GET を作らない | ✓ |
| 欠陥1の偽チェック | ✓ 無し（対処3が効いた） |

二重返却チェックは A(409)・C(400)・D(409) と**4回中3回入っていた**（B のみ無し）。
防御的に書きたくなる自然な実装で、Ch.1 の要件に記述が無いぶん、AIが「良かれと思って」足す。

### ★ここで分かった一般則

**ルールは、それが適用される項目そのものの中に書かないと守られない。**

- 欠陥1の禁止事項 → `仕込む欠陥リスト` の**該当項目の中**（`コードの見せ方`）に書いた → **1回で効いた**
- 返却API・予約APIの固定 → **別ブロック**に書いた → 振る舞いの列挙に加えても**効かなかった**

同じことが判定ブレ削減の Ch.1 でも起きている
（「推定で判定しない」を一般則として書くだけでは守られず、
論点そのものに `判定の既定: △` を埋め込む必要があった）。

### 対処

残る2点を、該当する欠陥項目の中に移した。

- **欠陥3の `コードの見せ方`** に「この API には認証チェック以外の検証を1つも書かない。
  特に二重返却チェックを入れない」を誤例（`if (lending.returnedAt) return 409 / 400`）つきで
- **欠陥5の `コードの見せ方`** に「GET /api/reservations は絞り込まず全件返す」を誤例つきで

|---|---|---|
| 欠陥5つ | ✓ | ✓ |
| 必ず正しく実装するもの | ✓ | ✓ |
| 絶対に入れないもの | ✓ | ✓ |
| 予約API GET は全件 | ✓ | ✓ |
| 返却APIに二重返却チェック無し | ✓ | ✓ |
