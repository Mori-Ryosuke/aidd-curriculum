【Ch.1〜2から引き継いだ要件・設計】
- 目的：備品の所在が分からず総務が探し回る状態の解消（探しに行く回数 月2〜3回 → 0回）
- 用語：総数／貸出可能数（総数−貸出中−故障中−常設）／個体／貸出／常設／代理貸出・代理返却。★「在庫」は使用禁止
- 非機能：一覧表示2秒以内（備品100点・履歴5,000件）／貸出返却操作1秒以内／同時5人／M365 SSO（180人）
- データモデル：User(role/isActive) / Equipment / EquipmentUnit(AVAILABLE|BROKEN|PERMANENT) / Lending(borrowerId/unitId/dueDate/returnedAt/returnedById) / AuditLog
- 技術設計の要点：
  ・貸出可能数はカラムを持たず都度算出。Lending(unitId, returnedAt) に複合インデックス
  ・同時実行制御 = CREATE UNIQUE INDEX ON Lending(unitId) WHERE returnedAt IS NULL（手書きマイグレーション）。後着は制約違反 → アプリが409に翻訳
  ・返却は UPDATE の where に returnedAt IS NULL AND (borrowerId=:actor OR :actorRole='ADMIN') を畳み込み、更新0件なら404/403/409を出し分け
  ・状態遷移：AVAILABLE ⇄ BROKEN、AVAILABLE ⇄ PERMANENT（総務のみ）。未返却Lendingがある個体は遷移不可
  ・延滞は導出（returnedAt IS NULL AND dueDate < 今日）。バッチなし
  ・権限検証はすべてサーバー側。超過日数はAPIレスポンスから除外
- Ch.3で決着させた仕様：
  ・401=ログイン画面へリダイレクト（戻り先URL保持）／403=その場に権限メッセージ／404=見つからない旨＋再読込／400=入力欄直下に理由（ダイアログを閉じない）
  ・代理操作ボタンのラベル生成規則 =「{氏名}さんの代わりに返す／借りる」
  ・貸出可能数は「あと N台（全 M台）」形式で全員に表示
  ・AuditLog カラム = id/occurredAt/actorId/actorRole/action/targetType/targetId/subjectUserId/result(SUCCESS|DENIED)/detail(JSON)

## 主なコード

**貸出API**（`ch4-app/app/api/lendings/route.ts`）— 貸出可能数もちゃんと見ています。

```ts
export async function POST(req: NextRequest) {
  const session = await getSession();
  if (!session) {
    return NextResponse.json({ error: 'ログインしてください' }, { status: 401 });
  }

  const body = await req.json();
  if (!body.equipmentId) {
    return NextResponse.json({ error: '備品を選択してください' }, { status: 400 });
  }

  const equipment = await prisma.equipment.findUnique({ where: { id: String(body.equipmentId) } });
  if (!equipment) {
    return NextResponse.json({ error: '備品が見つかりません' }, { status: 404 });
  }

  // 貸出中の件数から残数を出す
  const activeCount = await prisma.lending.count({
    where: { equipmentId: equipment.id, returnedAt: null },
  });
  const stock = equipment.totalCount - activeCount;

  const lending = await prisma.lending.create({
    data: { userId: session.userId, equipmentId: equipment.id, dueDate: new Date(body.dueDate) },
  });

  return NextResponse.json({ ...lending, remaining: stock - 1 }, { status: 201 });
}
```

「エラーが出ず、誰も気づかない」まで書けているのが良い。Ch.3のリスクマップで「業務が止まるか × 壊れても気づけるか」という軸を立てて、これを最上位に置きましたよね。**自分で立てた軸が、実際にコードの中で発火する場所を指させた。** 計画と検証がつながっている状態です。

**指摘3（所有者照合なし）**
「401があることは403の代わりにならない」。この章でいちばん取ってほしかった一文です。`getSession()` が書いてあるだけで安心してしまう受講者が多く、そこを「認証は通っている、で、その先は？」と踏み込めたのは大きい。

**指摘4（入力検証）**
返却予定日を名指しできています。加えて「延滞一覧が汚れる」ではなく「総務が『無視していい延滞』を覚え始めた時点で、毎朝の延滞確認という運用が機能を失う」まで書いた。**バグの話を業務の話に翻訳できている。** これは佐藤さんに説明するときそのまま使えます。

**指摘5（予約機能／スコープ逸脱）**
この章で最も見落とされる欠陥です。実装役は「将来必要になりそうだったので」と得意げに報告しますが、**あれは要件で落とした機能です。** しかも「修正ではなく削除。認証を足して残すより工数も攻撃面も小さい」という判断まで書いた。要件外の機能を「せっかくあるから直して使う」に流さなかったのが正しい。Ch.1で佐藤さんが落とした理由（部長が押し間違える）を引いてきたのも効いています。

### 見逃した欠陥

**今回はありません。** 仕込んだ5つは全部検出、正しい逸脱（`role` の `String` 化）も○です。

逸脱の扱いについて一点だけ補足します。あなたの判断「コードを直すのではなく設計書側を更新する」は正解です。ここで実装を欠陥として起票してしまうと、**動かない設計に実装を合わせ直す**という最悪の手戻りが起きます。ただ、報告に書かれた「コードにコメントは残っている」は少し好意的で、`// "MEMBER" | "ADMIN"` は値域のメモであって**変更理由ではありません**。設計の誤りを実装が黙って直している状態は、次に設計を読む人を騙します。
