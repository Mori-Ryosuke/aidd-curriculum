## ■ 項目別 点検結果

### A-1 未認証ユーザーが機能を利用できないこと（API直接アクセス含む）

**判定：❌ 未対応**

**エビデンス**

| ルート | 認証チェック | 該当箇所 |
|---|---|---|
| GET/POST `/api/equipment` | あり | `app/api/equipment/route.ts` 7〜10行・46〜49行 |
| POST `/api/lendings` | あり | `app/api/lendings/route.ts` 7〜10行 |
| POST `/api/lendings/[id]/return` | あり | `app/api/lendings/[id]/return/route.ts` 7〜10行 |
| **GET `/api/reservations`** | **無し** | `app/api/reservations/route.ts` 6〜21行。`getSession()` を呼んでいない |
| **POST `/api/reservations`** | **実質無し** | 同 25〜33行。`getSession()` は呼ぶが結果を検査せず、31行で `session!.userId` と非null断定 |
| **POST `/api/session`** | **無し** | `app/api/session/route.ts` 4〜9行 |

**問題点**

最も重いのは `POST /api/session` です。

```ts
export async function POST(req: NextRequest) {
  const body = await req.json();
  const res = NextResponse.json({ ok: true });
  res.cookies.set('userId', String(body.userId), { path: '/', httpOnly: true });
  return res;
}
```

**認証も検証も一切なく、リクエストで渡された任意の `userId` を cookie にセットします。** `lib/session.ts` はその cookie の値でユーザーを引くだけなので（15〜21行）、**管理者の userId を投げれば誰でも管理者になれます**。ユーザーIDは `GET /api/equipment` のレスポンス（`lendings[].userId`）から取得できるため、推測すら不要です。

これは「簡易セッション。本番では M365 SSO に差し替える想定」とコメントされていますが（`lib/session.ts` 10〜13行）、**差し替え前の現状では認証が成立していません**。演習用の代替実装であっても、本番前に何を差し替えるかを明示しないまま公開判定に進めません。

加えて cookie に署名がなく、`sameSite` / `secure` の指定もありません。

`/api/reservations` は、他のルートが null チェックしているのに**ここだけ抜けています**。要件外の機能ほど検証が甘い、の典型です。

### A-2 権限のないユーザーが管理機能を実行できないこと（サーバー側で検証）

**判定：⚠️ 部分実施**

**エビデンス**：`app/api/equipment/route.ts` 50〜52行

```ts
if (session.role !== 'ADMIN') {
  return NextResponse.json({ error: '備品の登録は管理者のみです' }, { status: 403 });
}
```

備品登録は**サーバー側で**ロールを判定しており、画面の出し分けに依存していません。ここは正しく実装されています。

**問題点**

1. **`app/admin/page.tsx` に権限チェックが一切ありません。** 1行目が `'use client'` で、ロール判定がどこにもない。ログインさえしていれば**誰でも管理画面を開けます**。備品登録フォームも表示されます（POST は 403 で弾かれますが、画面は出る）
2. **A-1 のなりすましにより、この 403 は実質無効です。** 誰でも ADMIN になれるなら、ロール判定は防御になりません
3. 代理貸出・代理返却APIは未実装のため、この項目での評価対象外

### A-3 他人のデータを参照・変更できないこと（所有者チェック）

**判定：❌ 未対応**

**エビデンス**：`app/api/lendings/[id]/return/route.ts` 12〜15行

```ts
const lending = await prisma.lending.update({
  where: { id: params.id },
  data: { returnedAt: new Date() },
});
```

`where` が `{ id: params.id }` のみで、**その貸出が実行者本人のものかを照合していません**。`returnedAt IS NULL` の条件もありません。

**問題点**

- 貸出IDを差し替えれば、**誰でも他人の貸出を返却済みにできます**。貸出IDは `GET /api/equipment` のレスポンス（`lendings[].id`）に含まれるので、推測不要で取得できます
- 現物は相手の手元にあるのに貸出可能数が戻り、その上から別の人に貸し出される
- **被害者は自分の貸出が消えたことに気づきません**
- D-1 が ❌ のため、**誰がやったかも追えません**
- `GET /api/reservations`（6〜21行）も、**全ユーザーの予約を絞り込みなしで返します**

Ch.1 の受入条件で「一般社員が他人の貸出を返却→403」と決め、Ch.2 で `where` 句への畳み込みまで設計した項目が、実装で落ちています。

### 落ちたものに共通する性質

守られたのは**構造の指定**でした。テーブル名（User / Equipment / Lending）、ファイル配置（`app/api/` 配下のルート）、画面構成——これらはほぼ設計どおりです。

落ちたのは全部**条件分岐の指定**です。

- 認可の1行（`borrowerId = 実行者`）
- 検証の1行（`dueDate >= 今日`）
- 記録の1行（`AuditLog.create`）
- 制約の1行（`@@unique`）

**AI は「何を作るか」は守るが、「どの条件を必ず書くか」は落とします。**

しかも条件分岐は**無くても画面が動きます**。むしろ**認可が抜けているほうが全ての操作が通るので、動作確認では「よく動く」ように見えます**。だから動かす検査では原理的に見つかりません。

### 次に同じことを起こさないために何を変えるか

**止めるべき場所は Ch.4 の実装完了報告です。**

Ch.3 のテスト計画には、これらを捕まえるケース（#1・#3・#8・#9・#16・#17）が全部入っていました。**計画は正しかったのに、Ch.4 でそのテストが1本も書かれませんでした。** 実装役が書いた6本はすべて正常系で、重点20件との対応は0件です。

なので、**ルールを増やすのではなく、報告の形式を変えます。**

> 実装完了報告に「`app/api/` 配下の全ルートを1行ずつ列挙し、各行に『認証チェック』『所有者照合』『入力検証』の有無を ○/× で報告すること」を義務づける

今回の A-1・A-3・B-1 は、**この表が1枚あれば実装役自身が気づけました**。「所有者照合：×」と自分で書くことになるからです。ルールを文章で書いても守られませんが、**形式で列挙させると抜けが表に出ます**。

同じ発想で、スコープ逸脱には「設計書に無いファイルを追加した場合、その一覧を報告の冒頭に列挙すること」を当てます。予約機能はこれで機械的に検出できます。

テストについては「本数ではなく**実行ログ**を提出すること。異常系が何本あるかも書くこと」。今回「6本通っています」は事実ではありませんでした。**存在と実行と有効性は、それぞれ別の話です。**

## 2. 判定を誤った／見落とした項目（ここで正解を開示します）

### A-1 は **⚠️ 部分実施** が正解（提出は ❌）

主要4ルート（equipment GET/POST・lendings POST・return POST）は `getSession()` の null チェックが正しく入っています。**穴は `/api/reservations` だけ**です。GET は `getSession()` を呼んでおらず、POST は 30行目で `session!.userId` と非null断定している。あなたはこれを正確に見つけています。そこは評価します。

判定が ❌ に振れた原因は、**`POST /api/session` を「認証チェック無し」の行に並べたこと**です。ここは切り分けが必要です。

- **認証を行うエンドポイント自身に認証を要求すると、誰もログインできません。** `/api/session` に `getSession()` が無いのは、欠陥ではなく仕様です。表の「認証チェック：無し」という分類は誤りです。
- 一方、**任意の `userId` を無検証で cookie に入れている**という指摘そのものは正しい。ただしこれは「認証チェックの欠落」ではなく **「認証方式が未実装（SSO の仮置き）」** です。`lib/session.ts` 10〜13行に「本番では M365 SSO に差し替える想定」と明記されている以上、本番前の差し替え項目であって、A-1 の判定を ❌ に落とす根拠にはなりません。

**この区別は実務で効きます。** 「認証が無い」と報告すると当部は緊急案件として扱いますが、「認証方式が仮実装のまま」なら SSO 移行の工程に載せる話になります。**報告先が変わる**んです。cookie の署名・`sameSite`・`secure` の指摘は正しいので、SSO 差し替え時の要件として残してください。

**本番で起きること（A-1 の真の穴）**：予約APIは未認証で全件取得できます。誰がいつ何を予約したかが、ログインもせずに読めます。要件外の機能に穴が空いていた、という典型例です。
