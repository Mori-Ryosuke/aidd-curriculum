# Ch.2 設計

## I. 目的

社内の備品貸出を記録し、**誰がどの備品を持っているかを常に見える状態にする**。
総務が備品を探しに行く回数を、月2〜3回から0回にする。

## II. 前提条件

**依存するもの**
- Microsoft 365（Azure AD）の SSO。全社員180人・派遣社員が保有済み。本システムはアカウントを自前で発行しない
- 初回ログイン時に、Azure AD の情報から User レコードを自動作成する（メール・氏名・部署）。事前の一括登録は行わない
- ロール（総務／一般）は Azure AD のグループでは管理せず、**本システムの User.role で持つ**
  - 理由：総務3名＋情シス1名の4件だけであり、グループ運用を情シスに依頼するほどの規模ではない。初期値は全員 MEMBER とし、稼働時に情シスが4名を ADMIN に設定する

**初期データ（★宿題1・2の回答）**

稼働前に、現行のExcel台帳から備品を移行する。移行は3段階に分ける。

| 段階 | 作業 | 担当 | 所要 |
|---|---|---|---|
| ① 台帳の転記 | Excelの品名・数量から `Equipment` と `EquipmentUnit` を生成。管理番号は仮番号で埋める | 情シスがスクリプトで実行 | 0.5h |
| ② 現物の確認 | 倉庫と各フロアを回り、管理番号シールの実番号・置き場所・故障中・常設を確認して紙に記録 | 総務3名 | 半日 |
| ③ 反映 | ②の結果を画面から入力（管理番号の修正、状態変更、置き場所） | 総務 | 2h |

★②を人手にした理由：常設分は佐藤さん自身が「たぶんもう少しある」と述べており、**Excelに載っていない個体が存在する**。台帳だけを写すと、稼働初日から実態とずれた状態で始まる。ここは現物を見ないと確定しない。

★移行スクリプトは冪等にする（再実行しても重複しない）。②で漏れが見つかったときに①からやり直せるようにするため。

**移行時点で貸出中のものの扱い（★宿題2）**

Excelには「持出者」の列があるが、記入漏れがある。そこで、
- 記入がある分 → その社員を借用者として `Lending` を作成。返却予定日は**移行日**とする（＝初日から超過表示される）
- 記入が無い分 → **移行専用ユーザー「不明（移行データ）」**を1件だけ作り、その借用者として `Lending` を作成

★専用ユーザー方式を選んだ理由：`Lending.borrowerId` を nullable にすると、以降すべての処理で null 判定が必要になる。専用ユーザーを1件置けば、**既存の代理返却の仕組みでそのまま閉じられる**。新しい仕組みを増やさない。

★閉じ方：総務が現物を見つけた時点で、総務メニューから「不明（移行データ）の代わりに返す」を実行する。誰が閉じたかは実行者として記録される。

★一覧での見え方：移行分は初日から超過表示になるため、総務メニューの延滞一覧の先頭に並ぶ。**これは意図した挙動**で、「移行直後にやるべき棚卸し作業リスト」として機能させる。一般社員の一覧では通常の貸出中として表示される（超過の強調は出ない）。

**稼働時期（★宿題3・保留）**
顧客に未確認。**保留とする。**
- 理由：移行②に総務3名の半日が必要で、繁忙期（2〜3月・9月）を避ける必要がある。総務の都合を聞かずに決められない
- **いつ誰が決めるか**：Ch.3 のテスト計画を作った時点で所要日数が見えるので、**私が佐藤さんに確認して決める**。期限は実装着手前

## V. 技術設計

### V-1. 貸出可能数の持ち方 — **カラムを持たず都度算出する**

```
貸出可能数 = EquipmentUnit のうち
              status = 'AVAILABLE'
              かつ 未返却の Lending に紐づかない  ものの件数
```

★カラムで持たない理由：更新経路が4つ（貸出・返却・故障登録・常設化）あり、どれか1つで更新を漏らすと**現物と台帳がずれる**。それは今回いちばん避けたい事象（総務が台帳を信用しなくなる）。1箇所の算出式に集約すれば漏れようがない。

★性能：備品100点・個体200件・履歴5,000件を想定。`Lending(unitId, returnedAt)` に複合インデックスを張り、一覧APIは `include` で1回のクエリにまとめる（N+1を出さない）。この規模なら2秒目標を満たせる見込み。**測定して超えたら、そのとき初めてキャッシュを検討する**（先に作らない）。

### V-2. 同時貸出の制御 — **DBの部分ユニーク制約に担保を置く**

```
BEGIN
  空き個体を1件 SELECT
  Lending を INSERT
COMMIT
```

★**トランザクションで囲むだけでは足りない。** 2人が同時に「同じ空き個体」を SELECT することを防げないため。

最終的な担保はここに置く：

```prisma
@@unique([unitId], name: "one_active_lending_per_unit")
// 実体は SQL の部分ユニークインデックス
// CREATE UNIQUE INDEX ... ON Lending(unitId) WHERE returnedAt IS NULL
```

- 後から INSERT した側は**制約違反で失敗する**
- アプリはその例外を捕まえ、**貸出可能数0と同じ応答（409）に翻訳する**
- ★アプリのロジックにバグがあっても、**同じ個体に未返却の貸出が2件並ぶことはDBが許さない**

★SQLite は部分インデックスに対応している。Prisma のスキーマだけでは表現できないため、マイグレーションSQLに直接書く。

### V-3. 返却の認可 — **where 句に畳み込む**

```sql
UPDATE Lending
   SET returnedAt = now(), returnedById = :actor
 WHERE id = :id
   AND returnedAt IS NULL
   AND (borrowerId = :actor OR :actorRole = 'ADMIN')
```

更新件数が0なら、貸出の存在を確認して 404 / 403 / 409 を出し分ける。

★`SELECT` して分岐する実装にしない理由：SELECT と UPDATE の間に別の返却が入ると**二重返却が通る**。where 句に条件を畳めば、**認可と二重返却防止が同じ1文で閉じる**。

### V-4. 入力検証

| 項目 | 条件 | 違反時 |
|---|---|---|
| dueDate | 本日以上 かつ 本日+60日以下 | 400 |
| equipmentId | 存在する / 貸出可能数1以上 | 404 / 409 |
| 代理貸出の borrowerId | 存在する / 実行者が ADMIN | 404 / 403 |
| 備品名 | 1〜50文字 | 400 |
| 目安日数 | 1〜60の整数 | 400 |

★すべて**サーバー側で検証する**。画面の `disabled` や `min` 属性は補助であって検証ではない。

### V-5. 状態遷移

**個体（EquipmentUnit.status）**
```
AVAILABLE ⇄ BROKEN      （総務：故障登録／修理完了）
AVAILABLE ⇄ PERMANENT   （総務：常設化／解除）
```
★**未返却の Lending がある個体は BROKEN / PERMANENT に遷移できない。** 先に返却が必要。
理由：貸出中の個体を故障扱いにすると、貸出可能数の算出から二重に外れて数が合わなくなる。

**貸出（Lending）**
```
（無し）──貸出──> 貸出中 ──返却──> 返却済
```
状態カラムは持たない。`returnedAt` の null / 非null で表す。

### V-6. 延滞の判定 — **導出。バッチを作らない**

```
延滞 = returnedAt IS NULL AND dueDate < 今日
超過日数 = 今日 - dueDate
```

★バッチで印を付けない理由：**バッチが止まった日に延滞が出なくなる**。総務は毎朝この一覧を見る運用なので、そこが止まると運用ごと止まる。監視も無い環境なので、止まったことにも気づけない。

★返却後も `dueDate` と `returnedAt` は残るので、**遅れた事実は履歴から復元できる**。

### V-7. 表示範囲の制御

| 情報 | 未認証 | MEMBER | ADMIN |
|---|---|---|---|
| 備品一覧・貸出可能数・置き場所 | 401 | ○ | ○ |
| 現在貸出中の借用者名・返却予定日 | 401 | ○ | ○ |
| 超過日数 | 401 | **自分の分のみ** | ○ |
| 貸出履歴（返却済み） | 401 | ✗ | ○ |
| 代理貸出・代理返却 | 401 | ✗ 403 | ○ |
| 備品・個体の登録編集 | 401 | ✗ 403 | ○ |

★**超過日数は API のレスポンスから除外する。** 画面で出し分けるのではなくサーバー側で落とす。画面に出していなくても、レスポンスに入っていれば漏れているため。

### V-8. 退職者の扱い（★宿題4）

- User に `isActive` を持たせる。退職時に情シスが false にする（レコードは消さない）
- **退職しても Lending は残る。** 借用者名の表示にも使う
- ★**未返却がある社員を退職扱いにしようとしたら、警告を出す**（ブロックはしない）。「未返却が2件あります。総務に確認してください」
  - 理由：退職手続きは総務の別業務なので、システムでブロックすると手続きが止まる。気づかせるに留める
- 履歴3年保持との整合：`isActive=false` でも Lending は3年残る。3年経過後の一括削除で User も参照されなくなったら削除可能とする（初期リリースでは削除処理は作らず、情シスの手作業）

### V-9. 一覧の並び順（★宿題5）

**備品名の五十音順（昇順）を既定とする。**
- 理由：佐藤さんが「名前順のほうが探しやすいのかな」と述べており、探す対象が決まっている人が見つけやすい
- 貸出可能数0のものも同じ順序に混ぜる（下に沈めない）。理由：目的は「誰が持っているか分かること」で、借りられない備品こそ誰が持っているかを見に来るため
- 貸出対象外（故障中・常設のみの備品）は**一覧の末尾**にまとめる

### V-10. 文字サイズ・表示密度（★宿題6・保留）

**保留とする。**
- 理由：設計に影響しない。稼働後に実機で調整するほうが確実
- **いつ誰が決めるか**：稼働1週間前の全社アナウンスの前に、**私が佐藤さんと部長に実機を見せて決める**
- ただし実装時の初期値として、本文16px以上・行間1.7以上を下限とする（老眼への配慮を初期値で担保しておく）

## VII. 備考（判断の理由）

- **個体（EquipmentUnit）を導入した代償**：移行が重くなる。数量を写すだけなら5分だが、管理番号・状態・置き場所を入れる作業が発生する。それでも導入したのは、数量カラムでは「3台のうち1台だけ故障中」を表せず、それが現在の「会議直前に無い」の直接の原因だから
- **AuditLog を最初から入れる**：代理返却の実行者記録が Ch.1 の Must にあるため。ついでに権限違反（403）も記録する。誰が何をしようとしたかは、事故のときに要る
- **監視が無いのは既知の弱点**：500エラーの検知が利用者の申告に依存する。今回のスコープ外だが、**弱点として明記して引き渡す**
- **`role` は enum ではなく String にする**：Prisma の SQLite コネクタが enum に対応していないため。アプリ側でバリデーションする。この差分は実装のコメントにも残す

## 【詳細】

### ✅ 書けている点

**V-2 の同時実行制御。ここが一番良い。**
「トランザクションで囲むだけでは足りない」と自分で書いて、担保をDBの部分ユニークインデックスに移したところ。この演習で最も差が出るポイントで、たいてい「トランザクションで排他制御する」で止まります。**アプリのロジックにバグがあっても、同じ個体に未返却の貸出が2件並ぶことはDBが許さない** ——この一文が書けているかどうかが、後で効いてきます。SQLiteが部分インデックスに対応していること、Prismaのスキーマでは表現できずマイグレーションSQLに手書きすることまで押さえているのは、実装まで見えている証拠です。

**V-3 の「where句に畳み込む」。**
認可と二重返却防止を1文で閉じた、という設計判断。SELECTしてから分岐する実装との差を理由付きで書いているので、実装者が勝手に読みやすい方（SELECT→分岐）に書き換えるのを防げます。

**V-1 と V-6 が同じ思想で通っていること。**
「状態を持たず都度計算する」で貸出可能数と延滞の両方を解いている。バラバラの判断の寄せ集めではなく、一本の方針になっている設計は読む側が予測できるので、レビューも実装も速くなります。しかも V-1 の性能のところで「測定して超えたら、そのとき初めてキャッシュを検討する（先に作らない）」と書いてある。これは良い判断です。

**移行設計（II）が運用まで届いている。**
台帳の転記／現物の確認／反映の3段階に分けて、担当と所要時間まで振ってある。特に「②を人手にした理由：Excelに載っていない個体が存在する」——ここ、Ch.1で佐藤さんから引き出した情報が設計判断に効いています。移行分を初日から超過表示にして、それを**意図した挙動**（棚卸し作業リストとして使う）と言い切ったのも、逃げずに決めています。

**VII の代償の記述。**
「個体を導入した代償：移行が重くなる」を自分で書いている。設計書に自分の判断のコストを書ける人は多くないです。

**加点しておきます。** AuditLogを最初から入れたこと、監視が無いのを既知の弱点として明記して引き渡すと書いたこと、3年後の削除処理を初期リリースで作らないと切ったこと。この3つは、この章で要求していた水準の上です。

### ⚠️ 抜けている点

**1. Ch.1のMust「代理操作ボタンへの対象者名表示」が、設計のどこにも出てこない。**

引き継ぎのMustにこう書いてあります：

&gt; 「自分の操作」と「他人の分の操作」の画面分離、代理操作ボタンへの対象者名表示

画面分離のほうは S1/S3（自分）と S4（総務メニュー）で満たしていますが、**対象者名の表示が落ちています**。これ、Ch.1で誤操作対策としてわざわざMustに上げた項目のはずです。総務が代理返却するとき、ボタンに誰の分か出ていないと、隣の人の貸出を閉じてしまう。実装者はS4の仕様を読んでも「ボタンのラベルに何を出すか」が分からないので、`返却` とだけ書いて終わります。

**2. 「総数」の表示が落ちている。**

Mustの備品一覧は「貸出可能数／総数／置き場所／借用者／返却予定日」の5点セットです。V-7 の表示範囲テーブルには貸出可能数・置き場所・借用者名・返却予定日はありますが、**総数がありません**。総務が「5台あるはずなのに2台しか見えない」を判断するための情報なので、これが無いと目的の半分が欠けます。個体数から導出できるとはいえ、画面に出すのか出さないのかは設計で決めておく話です。

**3. 異常時に「利用者に何が見えるか」が、在庫切れ以外は書かれていない。**

409（貸出可能数0）だけは「最早返却予定日と『先着順です』表示」まで書けています。ここは良い。でも他が空いています。

- 403（他人の貸出を返そうとした／一般社員が管理画面のAPIを叩いた）→ 画面には何が出る？　エラーメッセージ？　一覧に戻す？
- 400（返却予定日が61日先）→ どこにどう出す？　フォームの下？　ダイアログ？
- 401（セッション切れ）→ ログイン画面にリダイレクト？　エラー表示？

**特に401が困ります。** 総務が朝イチで印刷用一覧を開いたらセッションが切れていた、というのは毎週起きます。リダイレクトなのかエラー画面なのかで実装が全然違うのに、V-7 の表には `401` としか書いていない。実装者は自分で決めるしかなく、画面ごとにバラバラの挙動になります。

**4. AuditLog に何を記録するかが定義されていない。**

III の対応表には `AuditLog` が5回登場し、VII には「403も記録する」と書いてある。方針は良いんですが、**カラムが一つも決まっていません**。VIII に `lib/audit.ts` があるだけ。実装者は「actorId と、あと何を入れればいいのか」で必ず止まります。誰が・いつ・何に対して・何をしようとして・成功したか失敗したか——このうちどれを持つのかは、監査ログを「後で読む人」を想像しないと決まりません。Ch.5のセキュリティ監査でここを突かれます。

**5. データモデルのカラムが1か所に集まっていない。**（軽微）

`Lending.borrowerId`、`returnedById`、`dueDate`、`returnedAt`、`EquipmentUnit.status`、`User.role`／`isActive` ——読み進めれば全部拾えるので今回は○にしましたが、**5セクションに散っています**。schema.prisma を書く人は行ったり来たりすることになる。III に主要カラムの一覧を1枚足せば済む話です。
