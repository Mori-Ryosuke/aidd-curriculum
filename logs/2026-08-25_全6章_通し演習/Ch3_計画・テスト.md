# Ch.3 テスト戦略

## ★冒頭：前章から持ち越した宿題の決着（4件）

テストの期待値を書く前に、決めないと書けないものを決めました。

**(1) 401 / 403 / 400 / 404 時の画面表示**

| 状況 | 画面の挙動（全画面共通） |
|---|---|
| 401 未認証・セッション切れ | **ログイン画面へリダイレクト。戻り先URLを保持**し、ログイン後に元の画面へ戻す |
| 403 権限違反 | 画面遷移せず、その場に「この操作の権限がありません」 |
| 404 対象なし | 「この備品／貸出は見つかりませんでした」＋再読込ボタン |
| 400 入力エラー | **入力欄の直下**に理由を表示。ダイアログは閉じない（入力内容を消さない） |

★401 をリダイレクトにした理由：総務が朝イチで印刷用一覧を開いたときのセッション切れが日常的に起きる。エラー画面だとURLを打ち直すことになる。

**(2) 代理操作ボタンへの対象者名表示**（Ch.1 の Must）

ボタンのラベルを **`{借用者の氏名}さんの代わりに返す`** とする。代理貸出は **`{対象者の氏名}さんの代わりに借りる`**。
★ラベルの生成規則として仕様に書く。書かないと実装者は `返却` とだけ出す。

**(3) 備品一覧の「総数」表示**

**「あと N台（全 M台）」の形で全員に表示する。** M は個体数から算出。
★総務が「5台あるはずなのに2台しか見えない」と判断するための情報。隠す理由がない。

**(4) AuditLog のカラム定義**

```
id / occurredAt / actorId / actorRole
action        LEND | RETURN | PROXY_LEND | PROXY_RETURN
              | EQUIPMENT_CREATE | EQUIPMENT_UPDATE | UNIT_STATUS_CHANGE | DENIED
targetType    Lending | Equipment | EquipmentUnit
targetId
subjectUserId 操作の対象になった人（代理操作時の借用者）
result        SUCCESS | DENIED
detail        JSON（変更前後の値、拒否理由）
```
★`subjectUserId` を別に持つのが要点。`actorId` だけでは「誰が返したか」は分かっても「**誰の分を返したか**」が追えない。代理返却の苦情で必要なのは後者。
★`DENIED` を記録するのは、権限違反の試行を残すため。成功だけのログは事故の前兆を捨てている。

**(5) 稼働時期の見積もり** → 本文末尾「工数見積もり」に記載
**(6) 文字サイズ** → 保留のまま。テスト計画上は「実装時の初期値（本文16px・行間1.7）を満たしていることだけ目視で確認する」
**(7) 3年経過後のデータ削除** → **テスト対象外**（下記「捨てる判断」に明記）

## ■ 品質リスクマップ

重要度は**「業務が止まるか」と「壊れても気づけるか」の2軸**で判定した。

| 機能 | 壊れたとき何が起きるか | 気づけるか | 重要度 | テスト強化方針 |
|---|---|---|---|---|
| **貸出（貸出可能数の整合）** | 台帳上は貸出中なのに現物が無い／数が負になる。総務が台帳を信用しなくなり、また探しに行く＝目的が崩れる | **気づけない。**エラーが出ず静かにずれる | **高** | IT で同時実行を実測（10回反復）。境界値を全パターン |
| **認可（代理返却・他人の貸出）** | 他人の貸出を勝手に返却済みにできる。現物が戻っていないのに貸出可能数が戻り、次の人が空振りする | **気づけない。**被害者は自分の貸出が消えたことに気づかない | **高** | ST で API 直叩き。403 だけでなく **200 応答の中身**も検証 |
| **移行スクリプト** | 備品が重複登録される／個体が欠ける。稼働初日から台帳が壊れた状態で始まる | 移行直後なら気づける（目視できる） | **高** | IT で冪等性を実測（2回流して差分ゼロ） |
| **返却** | 返却が記録されず貸出可能数が戻らない／二重返却で数が増える | 半分気づける（借りた本人が気づく） | 中 | IT で状態遷移。二重返却を含む |
| **延滞判定** | 延滞が出ない／出すぎる。総務の毎朝の声かけ運用が空回りする | 気づける（総務が毎朝見る） | 中 | UT で日付境界を集中的に |
| **個体の状態遷移** | 貸出中の個体を故障中にできてしまい、貸出可能数の計算が二重に狂う | 気づけない | 中 | IT で遷移ガード |
| **備品一覧の表示** | 並び順が違う／表示崩れ | 目で気づける。翌日直せる | 低 | E2E の通しシナリオに含めるのみ |
| **検索** | 検索が効かない。50〜60点なので目視で代替できる | 気づける | 低 | **自動テストを作らない**（後述） |

★「貸出」と「認可」が高なのは、**壊れても誰も気づかない**組み合わせだから。表示崩れは目で分かるが、貸出可能数のズレは静かに蓄積する。

## ■ テスト戦略（4層 × 観点）

### UT（関数単体・DBはモック）

- **正常系**：貸出可能数の算出（`lib/availability.ts`）。AVAILABLE かつ未返却Lendingに紐づかない個体を数える
- **境界値**：延滞判定。返却予定日の当日／翌日／前日、超過0日／1日
- **境界値**：返却予定日バリデータ。本日／本日−1日／本日+60日／本日+61日
- **境界値**：備品名 0文字／1文字／50文字／51文字。目安日数 0／1／60／61
- **異常系**：返却予定日が空文字・不正な日付文字列
- ★**同時実行は UT に置かない。** モックの向こう側では競合が起きず、通っても何も保証しない

### IT（実DB使用）

- **正常系**：貸出→返却の1往復で貸出可能数が正しく戻る
- **境界値／同時実行**：**貸出可能数1の備品に2並列で貸出リクエスト**
  - 実行方法：テスト用DBに対し `Promise.all` で2件同時に貸出処理を呼ぶ。**10回繰り返す**
  - 合格条件：**成立1件・失敗1件、未返却Lending数=1、貸出可能数=0**（10回すべて）
  - ★この層に置いた理由：部分ユニークインデックスが効いているかは**実DBでないと再現できない**。かつ E2E では2ブラウザの同時操作を安定して作れない
- **異常系**：貸出可能数0の備品への貸出が拒否される（409）
- **異常系**：返却済みの貸出への再返却が拒否される（409）
- **異常系**：未返却Lendingがある個体を BROKEN に変更しようとして拒否される
- **正常系**：移行スクリプトを**2回実行して、備品・個体・Lendingの件数が1回目と同一**（冪等性）
- **正常系**：移行後、借用者不明のLendingが「不明（移行データ）」ユーザーに紐づいている
- **境界値**：備品0件の状態で一覧を取得してもエラーにならない

### ST（サーバー起動・HTTP経由）

- **セキュリティ**：一般社員のトークンで**他人の貸出IDに返却API** → **403**、かつDBの `returnedAt` が null のまま
- **セキュリティ**：一般社員のトークンで備品登録API → **403**
- **セキュリティ**：一般社員のトークンで代理貸出API → **403**
- **セキュリティ**：未認証で全APIを叩く → **401**
- **セキュリティ**：一般社員のトークンで備品一覧APIを叩き、**200応答のJSONに他人の超過日数が含まれていない**
  - ★403 の確認だけでは足りない。**弾かれずに返る200の中身**に見せてはいけない項目が混ざっていないかは別問題。画面に出していなくてもレスポンスに入っていれば漏れている
- **セキュリティ**：一般社員のトークンで貸出履歴（返却済み）を取得 → 含まれない
- **セキュリティ**：403 が発生したとき **AuditLog に `result=DENIED` の行が1件増える**
- **正常系**：代理返却時、AuditLog に `actorId=総務` かつ `subjectUserId=借用者` の行が記録される
- **異常系**：返却予定日に過去日／61日先を入れて 400
- **性能**：一覧APIの応答時間（下記）
- ★権限をこの層に置いた理由：画面のボタンを隠しても API を直接叩かれたら意味がない。ブラウザを経由しない層で確認する必要がある

### E2E（ブラウザ操作）

**正常系のみ・3シナリオに絞る。**
1. 一般社員が一覧を開き、備品を借りて、返す
2. 総務が備品を登録し、個体を追加し、1台を故障中にする
3. 総務が他人の貸出を代理返却する（**ボタンに「◯◯さんの代わりに返す」と出ていることを目視確認**）

★絞った理由：**E2Eツールは社内に実績がゼロ**。選定・習得・作成・保守をすべて自分でやる。1シナリオあたり作成に半日、実行に2〜3分。5営業日で回せるのは3本が上限。
かつ E2E は落ちたときに原因の切り分けができない（UI／API／DB のどこか）。異常系・境界値・権限は下位層に置き、**E2E は「画面がつながっていること」の確認に用途を限定する**。

## ■ 性能テストの計画

- **目標値**：Ch.1 で決めた「備品100点・履歴5,000件で一覧表示2秒以内」「操作1秒以内」「同時5人」

  - **同時5人**：`Promise.all` で5並列のリクエストを5回。**全リクエストの最大応答時間**を記録

- **実施者・時期**：私が、実装完了後の**3日目に1回**実施する
- ★1回しか測らない理由：CI/CD が無く毎回は回せない。変更のたびに測るのではなく、**リリース判定の材料として1回取る**

# 【詳細】

## 1. 押さえられている点

**重要度の2軸化。** これが今回いちばん効いてます。「業務が止まるか」だけで並べると認可が中くらいに落ちがちなんですが、「気づけるか」を掛けたことで最上位に来ている。実際そのとおりで、権限の穴は誰も気づかないまま半年経ちます。

**200応答の中身を独立ケースにした（#6）。** 403だけ確認して終わりにする計画が本当に多い。弾かれずに返る200のJSONに余計なフィールドが乗っているケースは、画面を見ている限り絶対に発見できません。Ch.2で「超過日数はAPIのレスポンスから除外」と決めた設計が、ちゃんと検証可能な形でテストに降りてきている。設計→テストの縦の線が通ってます。

**回帰テストの再実行ルール。** CI/CDが無いという前提を受けて自分でルールを作った。これは加点です。「最後にITを通したのはいつだっけ」は本当に起きます。

**落とす順番を先に決めたこと。** 5営業日で余裕ゼロという認識も正しい。優先度を「時間が無くなってから」決めると、必ず簡単なものから残して大事なものを落とします。

**Go/No-Go で「軽微」の判定者を自分から外したこと。** 作った本人が軽微と言う構図の危うさに気づいてる。これは経験がないと書けない項目です。

## 2. 抜けている点（判定には影響させませんが、本番で刺さります）

**(a) Ch.2 で決めた仕様のうち、テストに降りていないものが4件あります。**

- **常設（PERMANENT）・故障中（BROKEN）の個体が貸出可能数から除外されること。** UTに「AVAILABLEを数える」とは書いてありますが、重点ケース表に除外の確認がありません。総数M台の内訳が狂うと、総務が「5台あるのに2台しか見えない」で問い合わせてきます。宿題(3)で総数表示を入れたぶん、余計にここが目立つ。

**(d) 移行の②③に対する確認手順がありません。**

**(e) AuditLog の検証が「行が増えること」止まりです。**
