## 0. なぜ足すか

dev メンバーの現場は**チケット管理のチケットを AI に渡す**進め方（ツールは Backlog・Jira・GitHub Issues などが混在）。
現行の演習は、仕様の中身を書く力は鍛えられるが、**仕様をチケットとして AI に渡す工程**が無い。

| 現場で必ずやること | 現行の演習 |
|---|---|
| 1機能を、AI が1回で正しく実装できる大きさの子チケットに分ける | 無い。Ch.4 でアプリ全体を一括で「実装して」と頼む |
| 渡す前に、着手してよい状態か（DoR）を確かめる | 無い |
| 子チケットと受入条件を対応づける | 無い（章をまたぐ脱落は〈前章との整合〉で事後に数えるだけ） |
| 完了報告をチケット単位で受ける | 無い。実装役はアプリ全体で報告する |
| 実装依頼の定型文をテンプレートとして持つ | Ch.6 の指示書で作るが、置き場所に「チケットテンプレート」が無い |

既に近い部品はある：**Ch.2 の8セクションは、もともとチケットのテンプレート**（受講者ガイドの AI ペルソナ雛形に「このチケットの穴」とある）。受講者には「設計書」として見せていて、チケットだとは伝えていない。

---

## 1. 方針

- **特定のツールに依存しない書式**（Markdown のチケット本文）にする。ツールごとの欄への読み替え表を付ける
- **2段階で入れる**。第1段階は既存の測定結果をなるべく崩さない変更だけ。要件 ID の必須化は第2段階
- 学習目標の追加：「親チケットを、AI が1回で正しく実装できる子チケットに分け、着手条件を確かめてから渡せる」

## 2. 第1段階の変更

### 2-1. Ch.2：8セクションを「親チケット」と位置づける

- 出題・受講者ガイドで「この8セクションは、親チケット（機能単位のチケット）の本文です」と明示する
- **採点は変えない**（文言の変更だけ）

### 2-2. Ch.3：最後に「子チケットへの分割」を足す（★中心）

**提出フォーマットに追加**：

```
■ 子チケット（3〜8枚）
  親チケット（Ch.2）を、AI が1回で正しく実装できる大きさに分ける。1枚ごとに次の書式で書く
```

**子チケットの書式**（ツールに依存しない）：

```
# [子] <タイトル：動詞で終える。例「返却 API に所有者照合を入れる」>
親：<親チケットの名前>
## 目的            1文
## 対応する受入条件  Ch.1 の受入条件を引用（ID を振っていれば ID）
## やること
## やらないこと      このチケットの範囲外（他の子チケットでやること・やらないと決めたこと）
## 完了条件         テストの層と確認手段（Ch.3 の DoD から、このチケットの分）
## 依存            先に終わっている必要がある子チケット（無ければ「なし」）
## 参照            設計のどのセクションか（V-3 など）／守るべき指示資産
```

**DoR（着手してよいかの確認・5項目）**：

1. 目的が1文で書かれている
2. 対応する受入条件が1つ以上ある
3. やらないことが書かれている
4. 完了条件が、確認手段つきで書かれている（「動くこと」は不可）
5. 依存が書かれている（無ければ「なし」と書かれている）

**ツールへの読み替え表**（受講者ガイドに載せる）：

| 書式の項目 | Backlog | Jira | GitHub Issues |
|---|---|---|---|
| 親 | 親課題 | エピック／親 | 親 Issue（sub-issue） |
| タイトル | 件名 | 要約 | タイトル |
| 目的〜参照 | 詳細（本文） | 説明（本文） | 本文 |
| 依存 | 関連課題 | 課題リンク（ブロックする） | 本文に記載（または関連 Issue） |

**評価観点に1つ追加**：〈チケット分割〉（7観点 → 8観点）

| 何を数えるか | 達成 | 未達（言葉で定義） |
|---|---|---|
| (1) DoR 5項目をすべて満たす子チケットの数 ÷ 子チケットの数　(2) Ch.2 の引き継ぎの「スコープ Must」のうち、どの子チケットにも割り当てられていない機能の数（実装時に変更：Ch.2→Ch.3 の引き継ぎに受入条件の一覧が無いため） | (1) が全枚数 **かつ** (2) が 0 | 子チケットが無い、または1枚だけ |

★書く文字列（指定）：`**子チケット N枚。DoR を満たすもの M枚。どの子チケットにも無い Must の機能 K件。**`
★Ch.1.5 で第2期に回した Must は (2) に数えない（Ch.2 の〈前章との整合〉と同じ扱い）

**引き継ぎ**：Ch.4 への引き継ぎに【子チケット】を追加する（受講者が書いた子チケットをそのまま載せる）。

### 2-3. Ch.4：子チケットを渡し、子チケットごとに報告させる

- 受講者は「実装して」の代わりに、**子チケットを貼って**実装を依頼する
- 実装役は、子チケットごとに「実装したファイル／満たしたと主張する受入条件」を報告する
- **仕込む欠陥5つ・必ず正しく実装するもの・絶対に入れないもの・API 5本の固定は一切変えない**（Ch.5 の採点を守るため）
  - ★子チケットに「やらないこと：予約」と書いてあっても、欠陥5（要件外の予約機能）は入れる。
    報告では、該当する子チケットの「やらないこと」と食い違っていることに**触れない**（受講者が突き合わせて見つける）
- 検査の4観点は変えない。〈要件との実装ギャップ〉で、子チケットの「やらないこと」と生成ファイルを突き合わせた受講者には加点

### 2-4. Ch.6：指示書の置き場所に「チケットテンプレート」を足す（★作成者判断）

- 実装依頼の定型文（例：「APIルート全ファイルの所有者チェックの有無を一覧にして報告」）や完了報告の書式は、
  チケットテンプレートに置くのが現場の形。今は skills に押し込むしかない
- 4つ → 5つにすると、〈指示書の質〉の文字列 `置き場所 K/4` が `K/5` に変わり、**Ch.6 の測り直しが要る**

### 2-5. Ch.7：追加依頼を1件1チケットで起票させる

- Ch.7 の設計案 §2 の「② 仕分け・見積」を「② 起票・仕分け・見積」にする
- 5件の依頼をそれぞれ子チケットの書式で起票させ、DoR を通してから実装役に渡す
- 範囲外の依頼（Teams 通知など）は、起票したうえで「保留」にする（チケットを書かずに口頭で断らない）
