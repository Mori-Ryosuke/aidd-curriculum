## 4. AI入出力（原文）

```
【顧客の要望】
金曜の夕方、四半期の売上レビューが終わったあとの立ち話。EC事業部のPM・田中さんが、
スマホで競合サイトを開いてこちらに見せながら、ちょっと疲れた顔でこぼす。

「あー、うちの商品ページさ、そろそろレビュー機能つけたいんだよね。他社さん見てよ、
みんな入れてるじゃん？ うち、それがないから何となく安っぽく見えるって上からも
言われててさ。まあ、よくあるやつでいいんだけど、いい感じにお願いできる？
次のリリース、来月頭に乗せたいのよ。そんな時間ないと思うんだけど、ざっくりでいいから。
細かい所は…うーん、正直そこまで考えてなくて。とりあえずレビュー書けて、見れれば、
それでいいんじゃない？」

（田中さん、そう言いながらもう次の会議のカレンダー通知を気にしている様子。）

【演習ガイド】
- シチュエーション：新規0→1
- ヒント（標準）：顧客は非機能を自分からは話しません
- ミッション：AC付きユーザーストーリーまで詰める（5ステップ）
- 提出フォーマット：目的／ユーザーストーリー／スコープ／非機能／AC

さ、じゃあ何から聞きたい？ 私、次の会議まであと20分くらいしかないんだけど。
```

### T2：受講者の逆質問（1回目）

> レビューをつける目的はなんですか？
> 他者がつけてるからつけるというのは浅いと思います。
> 例えば、商品レビューを元に商品の改善をするためにつけるのか。
> 顧客同士でレビューを見合って購入意欲をあげたいのか。
> 具体的なイメージがあればしりたい。

### T3：田中さん役の返答

```
「うっ、鋭いね…確かに『他社がやってるから』は、まあ言い訳っぽかったよね、ごめん。

正直に言うとね、うちの商品ページ、直帰率がけっこう高くてさ。
特にスマホから来た新規のお客さんが、カートまで行かずに離脱してるのが気になってて。

たぶんなんだけど、初めての人って『これ本当に大丈夫かな』『思ったのと違ったらどうしよう』
みたいな不安があるんじゃないかと思うんだよね。

だから、どっちかっていうと後者かな。買おうか迷ってる人に、他のお客さんの声を見せて、
購入まで進んでもらいたいっていうのが本音。

商品改善に活かすっていうのも、まあできたら嬉しいけど、それは副次的というか…
今回は正直そこまで狙ってない。まずは購入率を上げたい、が一番大きいかな。」
```

### T4：受講者の逆質問（2回目・複数論点）

> KPIを知りたいです。
> どういうユーザーにレビューをかいてもらうのか？
> 悪口ばっかりにならないような工夫が必要とか
> 今の購入導線もしりたい。レビューがないなら商品説明だけで買ってると思うから
> そのページにレビューを載せる感じですか？
> あとレビューを書くのは購入者のみですよね？
> 社員とかがサクラではないけど社員レビューとかを入れるのはどう考えてますか？

### T5：田中さん役の返答（抜粋）

- **KPI**：数値目標未定、「一緒に考えてほしい」
- **投稿者**：深く考えてない、「戦略ある？」と逆質問返し
- **悪評対策**：懸念あり、判断委ねる
- **導線**：商品ページ（写真＋説明＋スペック＋カートボタン）の下部にレビューを載せるイメージ
- **投稿資格**：購入者限定は揺れ気味（「初期は少なくなる、オープンでどう？」と誘導）
- **社員レビュー**：「いやいやいや、それはダメでしょ（笑）」＝**Won't確定**

## 5. テスターとしての気づき（改善候補）

### 5-1. 良かった点（このまま活かしたい）

- **シーン描写の解像度**：金曜夕方／疲れ／会議20分／スマホで競合サイトを見せる — が具体的で、受講者が「顧客が急いでいる」プレッシャーを体感できる。良い没入感。
- **小出し開示の巧さ**：T3で「うっ、鋭いね」と受講者の質問品質を褒めてから真の目的を出す運びが自然。教育効果として、良い逆質問には手応えが返ってくると学べる。
- **キャラの倫理観**：T5「社員レビュー？いやいやいや」で顧客側の常識線が示されている。受講者の突飛な提案には顧客側から歯止めをかけてくれる。
- **判断の受け渡し**：KPI・投稿資格・悪評対策など、顧客が「一緒に考えて」「戦略ある？」と受講者側に判断を委ねる場面がある。これは実務でも起こる。良い演出。
- **提出フォーマットの明示**：ガイドで最終アウトプット形が示されているので、受講者はゴールから逆算できる。

### 5-2. 検討したい点（レビュアーの意見が欲しい）

1. **T5で6問一気に来た時の返答の均質さ**  
   質問密度が上がると、田中さんの返答も1論点ずつ丁寧に答えてしまう傾向がある（＝時間ない設定と少し矛盾）。実務では「あーごめん、それは後で」と切ったり、優先度をつけて返すのがリアル。**現状は親切すぎる**かも。

2. **顧客からの「逆質問返し」の頻度**  
   T5で「戦略ある？」「どう思う？」が2回登場。教育的には受講者に考えさせる良いパターンだが、多用すると **顧客なのに提案を求めすぎ** になる。1セッションで1〜2回が上限か？

3. **INVEST／MoSCoW実行タイミングの明示**  
   受講者は T6 で「INVESTで点検して」と依頼したが、これは受講者ガイドに書かれた「2〜5の手法はAIで回してよい」を読んでいたから。**顧客役エージェントが「情報がある程度溜まったら手法パスに移りましょう」と誘導する仕掛け** があると、受講者ガイドを未読でもハマる。

4. **タイム制約の運用**  
   「あと20分」設定が T5 でも維持されているが、実時間でセッションは既に長引いている。**タイムアップ演出**（田中さんが「もう行かなきゃ、続きはSlackで」と切り、受講者は残った情報で仮説を埋める）を入れると、実務プレッシャーが再現できる。

5. **隠し仕様の見え方（採点段階の設計）**  
   T7時点ではまだ採点フェーズに入っていない。「評価してください」で採点する運用と聞いているが、レビュアーには **隠し仕様セットの妥当性** と **採点ルーブリック** を別途共有する必要あり。今回のログには含まれていない。

6. **難易度「標準」の中身**  
   標準では「非機能・エッジケースがバランスよく隠れている」設計のはず。現時点で表出したのは主に機能要件と体制寄りの論点。**非機能（性能・セキュリティ・アクセシビリティ・多言語・法令＝景表法/ステマ規制）** が受講者側から出るか、あるいは顧客が最後まで沈黙するか、この確認が未完了。

7. **提出フォーマットとINVESTの繋がり**  
   提出フォーマットは「ユーザーストーリー」となっているが、INVESTで4本に分割した場合、**Mustに入れる粒度** をどう提出物に落とすかの指針が薄い。ガイドに例示があると受講者が迷わない。

### 5-3. コーチ役AI（Claude Code本体）としての気づき

- 受講者からの依頼「INVESTで点検して」を、私はエージェントに投げず自分で回答した。これは **手法系はコーチ側、キャラ演技系は顧客役エージェント側** という自然な役割分担になっているが、この境界はカリキュラム側で明文化した方が使い手が迷わない。
- 提案：`受講者ガイド.md` に「顧客への逆質問は spec-sparring-client、手法実行は普通のClaude／別スキルを使う」と明記。

## 9. 隠し仕様の中身（作成者の内部確認・レビュアー共有用）

エージェント定義ファイル `.claude/agents/spec-sparring-client.md` 内の隠し仕様を転記：

```yaml
題材ID: review-feature
シチュエーション: 新規0→1
初期要望: "商品ページにレビュー機能つけたい。いい感じにお願い。"
顧客像: EC事業部のPM（田中さん）。非エンジニア。忙しく、細かい仕様は考えていない。
真の目的: 購入検討者の不安を減らし、購入率を上げる（"他社もやってる"は表向き）
真のユーザー: 購入検討中の新規訪問者
must:
  - テキストレビューの投稿・表示
should:            # 手動運用で代替でき、初期は落とせる
  - 画像投稿
wont:
  - レビューへの返信機能
隠し論点（罠・受講者が掘らないと出てこない）:
  - 投稿者制限（購入者限定／サクラ対策）  ★顧客はわざと逆を言う
  - 表示性能（大量レビュー時の速度・並び順）
  - 通報フロー（不適切投稿対応）
非機能:
  - 1商品に大量のレビューが付いても表示速度が落ちない
用語のズレ:
  - "レビュー" に星評価が含まれるか不明確
エッジケース:
  - 同一ユーザーの二重投稿の扱い
  - レビュー0件時の表示
```

**評価ルーブリック（原文）**：達成／一部／未達 の3段階で以下6観点を判定。

| 観点 | 見るもの |
|---|---|
| 目的の明確化 | 真のビジネス目的にたどり着けているか |
| INVEST | 独立・価値・見積可能・Small・検証可能か |
| スコープ | MoSCoWで引き算し、Won'tを明示できているか |
| 非機能 | 性能・セキュリティ・運用を拾えているか |
| AC網羅性 | 正常系・異常系・境界値・具体例が入っているか |
| 隠し論点の発掘 | 「罠」を何個掘り当てたか |

## 10. 隠し仕様＆採点設計に対するカリキュラム視点の指摘

「田中さんの評価」ではなく **カリキュラム作成者・レビュアー向けのメタ評価** です。

### 10-1. 設計として上手いところ（維持したい）

- **「顧客がわざと逆を言う罠」**（投稿者制限で「誰でも書けた方が…」）は秀逸。今回の演習でも受講者が疑ってひっくり返した瞬間が最も学びが深い。実務あるある。
- **難易度別ヒントの粒度差**（易＝観点＋個数明示、標準＝観点のみ、難＝なし）は理にかなっている。
- **用語ズレ（星の有無）** をわざと曖昧化して、最終盤で田中さんから逆質問させる仕掛けが機能した。

### 10-2. 気になる点（優先度順）

#### 【最優先】隠し仕様が薄く、加点・減点基準が曖昧

受講者は隠し仕様を大幅に超える回答（ステマ規制／段階ロールアウト／可用性分離／KPI設計）を出した。これらはエージェントのアドリブで「加点扱い」となり 92点になったが、**評価ルーブリックに加点枠が定義されていない**ため、同じ回答でも別セッションだと点数がブレる可能性が高い。

→ **提案**：`bonus:` 枠を隠し仕様に追加（例：ステマ規制対応・可用性分離・KPI設計・アクセシビリティ）。

#### 【最優先】採点スコアの算出ロジック未定義

ルーブリックは「達成／一部／未達」の3段階のみ。**100点満点への換算式が無い**。今回92点の根拠が不明で、受講者間の比較やカリキュラム改善のPDCAが回せない。

→ **提案**：6観点×各16点＋隠し論点1個=α点 等の配点表を明記。「何点でSランク／Aランク」の閾値も。

#### 【高】mustの粒度が粗い（星評価の扱いが未定義）

隠し仕様のmustは「テキストレビューの投稿・表示」のみ。**星評価はmustか否かが不明**。受講者が「星必須＋テキスト任意」で提出しても、「星のみ」で提出しても、隠し仕様からは正誤判定不能。

→ **提案**：mustに「星評価（1-5）＋テキスト」を明記。用語ズレ解消後の期待動作をルールとして定義。

#### 【高】Won'tの照合基準が緩い

隠し仕様のwontは「返信機能」1つ。受講者はこれを **Could** に入れたが減点なし。「Won't一致必須／Could一致も可」等のルールが未定義。

→ **提案**：「wontに含めるべき項目は wont/could どちらでも可、shouldに入れたら減点」等の照合ルール明記。

#### 【中】顧客像・世界観の解像度が薄い

`顧客像: EC事業部のPM。非エンジニア。忙しい` しかない。エージェントは毎回アドリブで肉付けする（今回は「金曜夕方の立ち話・20分後に会議・スマホで競合サイト」等）。**セッション再現性が低い**。

→ **提案**：`situation_seed:` として情景の骨子を仕様側に固定（例：`場面:立ち話 / 時間制約:20分 / 心理:判断疲れ`）。

#### 【中】隠し論点が「機能・運用」寄りに偏り、法令・NFR系がゼロ

3つとも機能・運用系。標準難度なら景表法・ステマ規制・個人情報保護法・アクセシビリティのどれか1つは隠し論点として仕込みたい。

→ **提案**：標準難度では「機能系1つ／運用系1つ／法令 or NFR系1つ」のバランス構成に。

#### 【中】副次目的・KPIが仕様に無い＝アドリブ依存

田中さんが答えた「商品改善は副次的・優先度低」「CVR +10〜20%が妥当」は完全にエージェントのアドリブ。別セッションで違う回答が返る可能性。

→ **提案**：`副次目的:` `kpi_hint:` を隠し仕様に追加。

#### 【低】「顧客の初期反応」が全隠し論点に定義されていない

投稿者制限だけ「わざと逆を言う」が定義されているが、表示性能・通報フローは「自分から言及しない」だけ。掘られた時の反応がアドリブ。

→ **提案**：全隠し論点に「初期反応」を統一フォーマットで記載。

### 10-3. 総括

今回の演習が92点になったのは、**受講者が優秀だったのと同じくらい「田中さん役エージェントのアドリブが好意的に働いた」結果**。カリキュラムとして再現性・公平性を担保するなら：

1. 隠し仕様の情報量を **1.5〜2倍に増やす**（bonus枠、副次目的、初期反応、シチュエーションseed）
2. 採点ロジックを **定量化**（配点表・ランク閾値）
3. 標準難度の隠し論点に **法令 or NFR系を1つ含める**

このあたりが最優先の改善候補です。

## 13. 作成者の方針決定（レビュー時の判断軸）

上記12のAI側所感、及び§10のメタ評価に対する **作成者（森）の方針**：

### 採用しない改善案

- **採点の点数化（100点満点＋配点表）**：不採用。要件定義は正解が一つに定まらない領域。**観点別に達成／一部／未達＋良かった点／漏れた点／次の一手** で十分。むしろ点数化は「点取り」に意識が向いて学習の主眼をブラす。
- **タイム制約の一貫維持**：不採用。このカリキュラムの目的は **AIを活用して要件を整理すること** にあり、多少時間がかかっても良い。時間制約の演出は必須ではない。

### 部分的に受け入れる改善案

- **「Claude Code本体が代行しすぎる」問題**：確かに人間が判断して決める部分が薄れているという指摘は同意。ただし、方針としては **「AIが出したものを読んで、問題がなければ進める、あれば詰める」** という関わり方でOK。受講者が全プロンプトを自作する必要はない。**AIアウトプットのレビューと判断こそが人間の役割**、という立場でカリキュラムを設計する。

### 引き続き検討したい改善案

- 隠し仕様の情報量（bonus枠、副次目的、初期反応、シチュエーションseed）
- 顧客役の反論・抵抗パターンの追加
- mustの粒度、wont/couldの境界ルール
- 標準難度の隠し論点における法令/NFR系の追加

## 14. カリキュラムの立ち位置（明文化）

このカリキュラムのAI-人間の役割分担は以下の通り：

| 役割 | 担当 |
|---|---|
| 曖昧な顧客を演じる | `spec-sparring-client` エージェント |
| 逆質問の設計・手法（INVEST/MoSCoW等）の実行 | Claude Code本体（受講者の指示に応じて） |
| **AIアウトプットのレビューと採用可否判断** | **受講者（人間）** |
| 顧客への追加詰め・スコープ判断 | 受講者が方針決定、Claude Code本体が代行送信 |
| 最終仕様の妥当性判断 | 受講者 |

**受講者は「AI操縦者」であり、「プロンプト作成者」ではない**。プロンプトを一から書く練習ではなく、**AIが出した結果を批評し、方向修正する練習** がこのカリキュラムの中心。
