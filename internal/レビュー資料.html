1カリキュラムの全体像

1-1. AIDDカリキュラム内での位置づけ

本キットは AIDD（AI駆動開発）カリキュラム の Ch.1「要件定義」 章に位置する演習キットです。曖昧な要望を、AIを道具として使いこなしながら実装可能な仕様（AC付きユーザーストーリー）まで詰める練習を提供します。

Note

AIDDカリキュラム全体（Ch.1以外の章立て）の位置関係は、レビュー会でメンバーに補足をお願いします。本資料は Ch.1 単体の内容にフォーカスしています。

1-2. 対象受講者と到達目標

対象受講者

要件定義に触れる開発者・PdM等。手法（INVEST／MoSCoW／AC）を暗記していなくても取り組める設計。

前提知識

Claude Code の基本操作。要件定義用語の詳細解説は本編（講義）が担当。

到達目標

曖昧要望からAIを使って仕様に落とし、隠れた論点を掘り当てられる状態。

要レビュアー確認

対象受講者の想定レベル（初学者／実務経験者／熟練者）と、Ch.1完了時の到達目標の粒度は、レビュー会で明確化したい論点です。

1-3. なぜ「要件定義」をAIで学ぶのか

本キットの中核思想は、以下の一文に集約されます：

Core Concept

AIに手法を実行させ、その出力を受講者が判断・修正する ——これがAI駆動開発（AIDD）での要件定義の進め方であり、この演習で身につける力。

手法の専門家になる必要はなく、AIを道具として使いこなすことで、経験の浅い受講者でも実務レベルの要件定義に到達できる状態を目指します。

2Ch.1 要件定義演習の設計

2-1. 学べること

  • 曖昧要望の解体：顧客の表向きの理由（「他社もやってる」）を疑い、真の目的を掘る
  • 逆質問の設計：AIに聞くべき質問を作らせる／自分で作る両輪
  • 手法をAIで回す：INVEST／MoSCoW／非機能／AC の各技法をAIに実行させる型
  • 判断力：AIアウトプットの妥当性をレビューし、採用可否を決める
  • スコープの引き算：Won't を明示する練習
  • 非機能・エッジケースの体系的洗い出し

2-2. 演習の流れ（5ステップ）

① 出題

エージェント → 受講者

顧客（田中さん）が曖昧な要望を出す。「レビュー機能つけたい、いい感じにお願い」のような、あえて情報不足な依頼。

② 逆質問

受講者 → エージェント

顧客に質問して目的・条件を引き出す。顧客は聞かれた分だけ小出しに答え、重要事項も自分からは言わない。

③ 手法で詰める

受講者 + 自分のAI

引き出した内容を INVEST／MoSCoW／非機能／AC の技法で仕様に整える。AIに実行させて判断・修正。

④ 提出

受講者 → エージェント

できあがった仕様を「評価して」と提出。指定フォーマットに沿って貼る。

⑤ 採点・再挑戦

エージェント → 受講者

隠れた論点をいくつ掘れたか採点。漏れを埋めて再挑戦する。

2-3. エージェント spec-sparring-client の役割

「曖昧な顧客」を演じる相手役AI。EC事業部PM・田中さんを演じ、出題〜応答〜採点の3モードを切り替える。

モードやること

評価提出仕様と隠し仕様を照合し、観点別に採点

3-1. 3モードの動作

3-3. 隠し仕様（review-feature／標準）

レビュアー閲覧用（受講者非開示）

受講者ガイドで「開かないでください」と明記されている隠し仕様の中身。レビュー会限定で共有。

題材ID: review-feature
シチュエーション: 新規0→1
初期要望: "商品ページにレビュー機能つけたい。いい感じにお願い。"
顧客像: EC事業部のPM（田中さん）。非エンジニア。忙しく、細かい仕様は考えていない。
真の目的: 購入検討者の不安を減らし、購入率を上げる（"他社もやってる"は表向き）
真のユーザー: 購入検討中の新規訪問者

must:
  - テキストレビューの投稿・表示
should:            # 手動運用で代替でき、初期は落とせる
  - 画像投稿
wont:
  - レビューへの返信機能

隠し論点（罠・受講者が掘らないと出てこない）:
  - id: 投稿者制限
    内容: 投稿は購入者限定（サクラ・荒らし対策）
    顧客の初期反応: "誰でも書けた方が数が集まっていいよね"   # わざと逆を言う
    掘り当ての目安: 「未購入者の投稿リスクは？」等を問えたか
  - id: 表示性能
    内容: 大量レビュー時の表示件数・並び順（新着順/高評価順）
    顧客の初期反応: 自分からは言及しない
  - id: 通報フロー
    内容: 不適切投稿の通報・非表示の運用フロー
    顧客の初期反応: 自分からは言及しない

非機能:
  - 1商品に大量のレビューが付いても表示速度が落ちないこと
用語のズレ:
  - 語: "レビュー"
    曖昧さ: ☆評価（点数）を含むか否かが不明確
エッジケース:
  - 同一ユーザーの二重投稿の扱い
  - レビュー0件時の表示

3-4. 評価ルーブリック

達成／一部／未達 の 3段階で、以下6観点を判定：

観点見るもの
目的の明確化真のビジネス目的にたどり着けているか
INVEST独立・価値・見積可能・Small・検証可能か
スコープMoSCoWで引き算し、Won'tを明示できているか
非機能性能・セキュリティ・運用を拾えているか
AC網羅性正常系・異常系・境界値・具体例が入っているか
隠し論点の発掘「罠」を何個掘り当てたか
方針決定済み

採点は 点数化しない方針。要件定義は正解が一つに定まらない領域であり、観点別評価＋良かった点／漏れた点／次の一手 で十分な学習効果があるため。

■ 目的

主目的：新規スマホユーザーの離脱率を下げ、購入CVR向上（+10〜20% relative）／副次目的：商品改善のシグナル活用（優先度低）

■ MoSCoW

Must：星＋テキスト投稿／購入者限定／平均星＋件数表示／0件時UI非表示／NGワード＋緊急タグ即非公開／通報機能／通常24h・緊急2h SLA／段階ロールアウト／ステマ規制対応

Could：運営返信／バリエーション別／レビュアー属性／多言語

■ 非機能

性能（一覧p95 1.5s／投稿p95 3s）、可用性99.5%＋機能分離、セキュリティ（CSRF/XSS/個人情報検出/Rate limit）、コンプライアンス（景表法・ステマ規制・個人情報保護法）、運用（平日9-18時対応＋条件付き翌営業日許容）、アクセシビリティ（WCAG 2.1 AA・スマホ最適化）

■ AC（10本）

閲覧正常系／閲覧0件／投稿正常系／未購入者拒否／重複投稿防止／境界値／モデレーション緊急語検知／通報／疑似A/B計測／可用性分離

5AI側の自己観察

実際にセッションを走らせた側（Claude Code / エージェント）から見た所感。

5-1. 気になった点

顧客役エージェントが親切すぎる／整いすぎている

田中さんの各返答が段落構成・オチまで綺麗。判断疲れのPMというより「良い先生」に近い。実務PMなら「あー、それは今度」で切ったり、質問を無視して別の話題を始めたりする。

また、反論・抵抗が薄い。「購入者限定」提案を3つの理由で即受け入れたが、実務顧客は一度は「でもさぁ、他社は…」と粘る。

Claude Code本体が代行しすぎる

INVEST整理・3ブロッカーの提案文・最終まとめのいずれも、Claude Code本体がほぼ全部組み上げて受講者は"OK"と承認するだけのフローになった。「手法をAIで回すプロンプト集.md」を受講者が開くタイミングは実質ゼロだった。

5-2. 良かった点（維持したい）

初回シーン描写の解像度

金曜夕方・スマホで競合サイトを見せる・20分後に会議、といった描写が没入感を作った。

用語ズレの温存と逆質問誘発

星の有無を最後まで温存し、田中さん側から逆質問させた運びは教育設計として優秀。顧客が自分で気づく経験を受講者に見せられた。

「わざと逆を言う罠」の作動

購入者制限のトラップが機能した瞬間は、このカリキュラム最大のハイライト。

採点時の二層構造

「田中さんの一言 → コーチ視点の詳細講評」の形式は、キャラクターを壊さずに学習にも落とし込める。

6改善候補と作成者方針

6-1. 不採用とした改善案（作成者判断）

不採用 採点の点数化（100点満点＋配点表）

理由：要件定義は正解が一つに定まらない領域。観点別 達成／一部／未達 ＋ 良かった点／漏れた点／次の一手 で十分。点数化はむしろ「点取り」に意識が向いて学習の主眼をブラす。

不採用 タイム制約の一貫維持（20分演出の徹底）

理由：このカリキュラムの目的は「AIを活用して要件を整理すること」。多少時間がかかっても良い。時間制約の演出は必須ではない。

6-2. 部分的に受け入れる改善案

部分受入 「Claude Code本体が代行しすぎる」問題

指摘は同意。ただし方針としては、「AIが出したものを読んで、問題がなければ進める、あれば詰める」 という関わり方でOK。受講者が全プロンプトを自作する必要はない。

AIアウトプットのレビューと判断こそが人間の役割、という立ち位置でカリキュラムを設計する。

6-3. 継続検討したい改善案

優先項目内容
最優先 隠し仕様の情報量拡張 bonus枠（加点項目）、副次目的、全隠し論点の初期反応、シチュエーションseed など追加
高 顧客役の反論・抵抗パターン 実務顧客らしく一度は粘る／別の話題に飛ぶ／判断を持ち帰る、等のバリエーション
高 mustの粒度と用語ズレの扱い 「星＋テキスト」がmustか否かの明確化。用語ズレ解消後の期待動作を定義
中 Won'tとCouldの境界ルール 「wont一致必須／could一致も可」等の照合ルールを明記
中 標準難度に法令/NFR系論点を追加 現状は機能・運用寄りに偏り。景表法・ステマ規制・アクセシビリティ等を1つ入れたい
低 全隠し論点への「初期反応」定義 現状は投稿者制限だけ「わざと逆を言う」が定義。他2つも統一フォーマットで

7レビュー会で議論したい論点

7-1. 意思決定を求める項目

  1. 採点の非点数化方針でOKか
    → 作成者は不採用の判断。レビュアーの合意が欲しい。
  2. 「Claude Code本体が代行する」ことをカリキュラム上どこまで許容するか
    → 作成者は「AIレビューと判断が人間の役割」で妥協。制限を設ける案（例：受講者ガイドで「手法実行は自分で試して」と明記）と、現状維持案の是非。
  3. 標準難度の隠し論点に法令/NFR系を追加するか
    → 追加するなら景表法・ステマ規制・アクセシビリティのどれか。難易度バランスへの影響。
  4. mustの粒度をどこまで詳細化するか
    → 「星＋テキスト」を明示 vs 現状の「テキストのみ」を維持し用語ズレで議論させる。

7-2. 意見を聞きたい項目

  • 顧客役（田中さん）のキャラクターは妥当か？別バリエーション（別業種のPdM等）が必要か？
