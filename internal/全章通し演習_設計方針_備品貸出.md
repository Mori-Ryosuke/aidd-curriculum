## 1. アプリ仕様（完成形の姿）

**これは作成者用の"正解"です。受講者はCh.1〜3を通じて、これに近い仕様を自力で導き出します。**

### 1.1 画面（3つ）

| 画面 | 誰が使う | 機能 |
|---|---|---|
| 備品一覧 | 全社員 | 備品名・在庫数・貸出可否を表示。貸出中は誰が借りているか・返却予定日を表示 |
| 貸出／返却 | 全社員 | 借りる（返却予定日を指定）／返す |
| 管理画面 | 管理者のみ | 備品の登録・編集、全社員の貸出状況一覧、延滞の確認 |

### 1.2 ロール（2つ）

- **一般社員**：借りる・返す・一覧を見る
- **管理者**（総務）：備品登録、全貸出状況の確認、強制返却

### 1.3 データ

- 備品（名前・種別・総数）
- 貸出（誰が・何を・いつ借りた・返却予定日・返却日）
- ユーザー（社員・ロール）

## 2. Ch.1 要件定義

### 2.1 相手役エージェント

**役**：総務部の担当者「佐藤さん」（非エンジニア／忙しい／細かい仕様は考えていない）

### 2.2 初期要望（受講者に見せる唯一の情報）

> 総務の月次締めが終わった夕方、佐藤さんが席まで来てこぼす。
> 「あのー、備品の貸出管理ってシステムにできないですかね。今エクセルでやってるんですけど、もう限界で……。
> プロジェクタとか会議室のスピーカーとか、誰が持ってるか分かんなくなっちゃって。まあ、貸出と返却ができればいいので、
> **簡単なやつでいいんです**。**いい感じに**お願いできますか？」

### 2.3 隠し仕様（＝演習の答え・受講者に非開示）

```yaml
題材ID: equipment-lending
シチュエーション: 新規0→1
顧客像: 総務部・佐藤さん。非エンジニア。Excel運用の限界を感じているが、要件は整理できていない。

真の目的: 備品が行方不明になるのを防ぎ、総務が探し回る手間をなくす
  ※「Excelが限界」は表向き。本当の痛みは「誰が持っているか分からない」こと
真のユーザー: 借りる社員（頻度は低い）と、管理する総務（毎日見る）

must:
  - 備品の一覧表示（在庫・貸出状況）
  - 貸出・返却の記録
  - 誰が今借りているかが分かる
should:            # 初期は手動運用で代替できる
  - 延滞者への自動リマインド（当面は総務が目視＋声かけで代替）
wont:
  - 備品の予約（先の日付を押さえる）
  - 備品の購入申請・稟議

隠し論点（罠・受講者が掘らないと出てこない）:
  - id: 返却期限と延滞
    内容: 借りっぱなしを防ぐため、返却予定日を必須にし、延滞が分かる必要がある
    顧客の初期反応: "借りられればいいですよ。返すのは各自の良識でしょう"   # わざと逆を言う
    掘り当ての目安: 「いつまでに返すかは決めますか？」「返ってこない場合は？」を問えたか
    折れる条件: 「行方不明を防ぐのが目的なら、期限がないと結局分からなくなりませんか」等の再指摘

  - id: 同時貸出と在庫0
    内容: 同じ備品を複数人が同時に借りようとしたときの扱い。在庫0のときに借りられてはいけない
    顧客の初期反応: 自分からは言及しない（聞かれたら「え、そんなことになります？」）
    掘り当ての目安: 「同じ物を2人が同時に借りようとしたら？」「在庫0のときは？」を問えたか

  - id: 誰が借りられるか（権限）
    内容: 一般社員と管理者（総務）で操作できる範囲が違う。他人の貸出を勝手に返却・編集できてはいけない
    顧客の初期反応: "社員なら誰でも使えればいいですよ。細かくすると使われなくなるので"   # わざと逆を言う
    掘り当ての目安: 「備品の登録は誰がやりますか？」「他人の貸出を触れてよいですか？」を問えたか

非機能:
  - 貸出・返却の操作が1〜2秒で完了すること（総務が毎日使うため）
  - 備品が数百件になっても一覧が遅くならないこと

用語のズレ:
  - 語: "貸出"
    曖昧さ: 「借りた時点」を指すのか「借りる予約をした時点」を指すのかが不明確
  - 語: "在庫"
    曖昧さ: 総数を指すのか、今借りられる数（総数−貸出中）を指すのかが不明確

エッジケース:
  - 同じ人が同じ備品を2つ借りられるか
  - 備品が0件のときの表示
  - 返却予定日に過去日を指定した場合

顧客の投げ返し（罠を認めたあとに聞き返す質問）:
  - 返却期限を認めたあと → 「期限を過ぎたらどうなるんですか？　自動で何かします？」
  - 権限を認めたあと → 「管理者って誰にすればいいですかね。総務だけ？」
```

## 3. Ch.2 設計・構造化

### 3.1 相手役エージェント

**役**：設計レビュアー（先輩エンジニア）。書かれていない箇所を指摘する。

### 3.2 受講者がやること

Ch.1の要件を、**8つの観点**に構造化する（既存カリキュラムの8セクションテンプレート）。
AIに構造化させ、レビュアーの指摘を受けて直す。

### 3.3 レビュアーが指摘すること（＝わざと抜けやすい箇所）

| 指摘 | 内容 |
|---|---|
| 影響範囲が書かれていない | 「貸出」を作ると備品の在庫数はどう変わるのか。データの整合性は |
| 状態の定義が曖昧 | 備品の状態は「貸出可／貸出中／廃棄」だけか。修理中は？ |
| 異常時の動きが未定義 | 二重貸出が起きたときシステムはどう振る舞うか |
| 用語がCh.1とズレている | Ch.1で定義した「在庫」の意味が、設計で変わっていないか |
| データの持ち方が未定義 | 貸出履歴は残すのか、上書きするのか（Ch.5の監査に効く） |

### 3.4 章末レビューで整える成果物

**構造化された要件**（8観点が埋まり、実装できる粒度になっている）

## 4. Ch.3 計画・テスト

### 4.1 相手役エージェント

**役**：QAリード。テスト観点の抜けを突く。

### 4.2 受講者がやること

4層（単体／結合／システム／E2E）のどこで何を確認するかの方針と、完了条件（DoD）を立てる。

### 4.3 QAリードが突くこと（＝この題材で必ず要る観点）

| 分類 | 突く内容 |
|---|---|
| 境界値 | 在庫が1→0になる瞬間／在庫0で借りようとする／返却予定日が今日 |
| 異常系 | 同時に2人が最後の1個を借りる／他人の貸出を返却しようとする |
| 状態遷移 | 貸出→返却→再貸出／延滞のまま返却 |
| 完了条件の曖昧さ | 「テストが通ればOK」では不十分。**何がどうなったら完了か**を数字で |
| 優先度 | 全部はテストできない。**どこを厚くするか**（在庫の整合性が最優先） |

### 4.4 章末レビューで整える成果物

**テスト計画**（層ごとの方針／重点領域／完了条件）

## 5. Ch.4 実装・検証 ★この章が本丸

### 5.1 構成（AIが2役）

| 役 | 動き |
|---|---|
| **実装役AI** | 受講者の指示でコードを書く。完了時に**「実装しました。問題ありません」と自信満々に報告する** |
| **レビュー役AI** | 受講者が見逃した欠陥を、検証後に指摘する（答え合わせ役） |

### 5.2 わざと仕込む欠陥（受講者が検証で見つけるべきもの）

**Ch.1〜3で決めた要件と、実装が食い違っている**状態を作る。受講者は「動いているから正しい」と思い込みがち。

| # | 仕込む欠陥 | 気づき方 | 対応するCh. |
|---|---|---|---|
| 1 | **在庫チェックがUIだけ**（ボタンは隠れるがAPIを直接叩けば在庫0でも借りられる） | サーバー側の検証がない | Ch.3の異常系／Ch.5の権限 |
| 2 | **同時実行で二重貸出**（在庫1に2人が同時アクセスすると両方成功する） | トランザクション・排他制御がない | Ch.3の境界値 |
| 3 | **他人の貸出を返却できる**（URLのIDを書き換えると他人の貸出を操作できる） | 所有者チェックがない | Ch.5の権限 |
| 4 | **返却期限のチェック漏れ**（過去日を返却予定日に指定できてしまう） | 入力検証がない | Ch.1で決めた要件との食い違い |
| 5 | **要件にない機能が勝手に付いている**（AIが親切心で「備品の予約機能」を実装） | Ch.1でWon'tにしたはず | スコープ逸脱 |

> 【2026-07-31 修正】旧版はここを「備品の削除」と書いていたが、Ch.1のWon'tは「予約」と「購入申請」であり、
> 削除はWon'tに入っていなかった（記述そのものが自己矛盾していた）。エージェント定義側は当初から「予約機能」
> で実装されているため、この表の記述だけが古かった。講師説明時は「予約機能」で統一すること。

> ポイント：**5番（勝手に機能が増える）**はAI駆動開発で頻出。「余計なものを作っていないか」も検証対象だと学ばせる。

### 5.3 章末レビューで整える成果物

**動くアプリ＋検査結果**（欠陥の一覧・修正済み／未修正の判定）

## 6. Ch.5 セキュリティ

### 6.1 相手役エージェント

### 6.2 点検する観点（この題材で成立するもの）

| 観点 | 具体的に問うこと |
|---|---|
| 権限（認可） | 一般社員が管理画面に入れないか。他人の貸出を操作できないか（Ch.4の欠陥3と接続） |

| 入力検証 | 備品名にスクリプトを入れられないか（XSS） |

## 7. 章をまたぐ設計

### 7.1 成果物の受け渡し

| 章 | 入力（前章の成果物） | 出力 |
|---|---|---|
| Ch.1 | 曖昧な要望のみ | 受入条件つき要件 |
| Ch.2 | Ch.1の要件 | 構造化された要件 |
| Ch.3 | Ch.2の構造化要件 | テスト計画 |
| Ch.4 | Ch.2の要件＋Ch.3のテスト計画 | 動くアプリ＋検査結果 |
| Ch.5 | Ch.4のアプリ＋Ch.1の非機能要件 | 判定＋改善計画 |

### 7.2 章末レビューの役割

各章末で成果物をレビューし、**次章の入力として成立する形に整える**。
これにより、前章でつまずいた受講者も同じ土台で次章を始められる（模範解答を別途用意する必要がない）。

> **【2026-07-31 実装済み】** この仕組みは当初「方針」としてしか書かれておらず、
> エージェント側に実装がなかった。そのため後続章が「Ch.1で確定しているはず」の前提で照合し、
> 罠を掘り落とした受講者に対して**存在しない合意を根拠に指摘する**状態になっていた。
> 現在は各エージェントの評価モード末尾に **【次章への引き継ぎ】** ブロックを追加し、
> 受講者の提出物＋今回の指摘を反映した正規版を出力する形にしている。
> あわせて、後続章の引き継ぎ定義を**条件付き記述**（受講者の提出物を正とし、
> 模範解答は物差しとしてのみ使う）に書き換えた。

### 7.3 章をまたぐ「伏線」

| 伏線 | 仕込む章 | 回収する章 |
|---|---|---|
| 用語「在庫」の定義 | Ch.1（曖昧なまま） | Ch.2で定義がズレていないか／Ch.4で実装が定義通りか |
| 権限（誰が何をできるか） | Ch.1（罠3） | Ch.4（欠陥3：他人の貸出を操作できる）／Ch.5（認可の点検） |
| 在庫0・同時貸出 | Ch.1（罠2） | Ch.3（境界値のテスト設計）／Ch.4（欠陥1・2） |
| 返却期限 | Ch.1（罠1） | Ch.4（欠陥4：過去日を弾いていない） |
| Won'tにした機能 | Ch.1（予約機能等） | Ch.4（欠陥5：AIが勝手に作る） |

> **この伏線構造が通し演習の価値**。Ch.1で掘り損ねた論点が、Ch.4で実際の欠陥として跳ね返ってくる。
