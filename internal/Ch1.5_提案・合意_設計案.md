### なぜ Ch.1 と Ch.2 のあいだか

- Ch.1 の相手は**担当者**（佐藤さん）。要件は決められるが、**予算・時期・やらないことの最終判断**は持っていない

## 1. 学習目標（行動で書く）

この章を終えた受講者は、次のことができる。

1. 担当者と合意した要件を、**決裁者の判断材料（効果・費用・時期・リスク）に組み替えて** A4 1枚で示せる
2. **2〜3の選択肢を、それぞれ「何を失うか」つきで**示し、推奨案とその理由を言える
3. 機能単位で工数を積み、**前提条件と幅**つきで概算を出せる（AIに積算させ、自分で判断する）
4. 制約（時期・工数）に対して**何を削っても目的が崩れないか**を示し、スコープを交渉できる
5. **担当者が決めてよいことと、決裁者が決めるべきこと**を仕分け、後者を決裁者に上げられる

## 2. 章の流れ

```
① 出題         決裁者（総務部長）が「来週15分だけ時間を取る」と言ってくる
② 提案書を作る   Ch.1 の引き継ぎを、A4 1枚の提案書＋概算見積に組み替える（AIで積算・下書き可）
③ 説明する      部長に提案する。部長は質問・反論してくる（聞かれたことにしか答えない点は佐藤さんと同じ）
④ 交渉する      部長が制約を出す → 案を修正して再提示（何度でも可）
⑤ 提出・採点    合意した計画を提出 → 「Ch.2 への引き継ぎ」に【合意した計画】が加わる
```

所要時間（机上）：60〜90分

## 3. 相手役の設定

- エージェント名（案）：`proposal-decision-maker`
- 人物：**総務部長**（佐藤さんの上長）。Ch.1 で佐藤さんが言及した人物と**同一**
  - 既存の言及と揃える：老眼／自分では操作しない（総務に「これ借りるわ」と言う側）／ボタンが並ぶと間違える
  - ※ `spec-sparring-client` / `handover-retrospective` に部長の名前・追加設定があれば**そちらに合わせる**（要確認）
- 話し方：忙しい。結論を先に求める。技術用語が出ると「つまり？」と聞き返す
- 15分しか無い設定。**長い説明には「で、いくらかかって、いつ使えるの」と割り込む**

### 部長が最初に言うこと（出題文の骨子）

> 佐藤から聞いてる。備品のやつね。来週15分取るから、紙1枚で持ってきて。
> 私が知りたいのは、いくらかかるのか、いつ使えるのか、それでうちは何が良くなるのか。それだけ。

### 隠し事情（部長は聞かれない限り言わない）

#### H2 の詳細（世界観：内部監査）

2026-10-19 に追加を決定。演習内の基準日は 2026-06-01。

**事実（部長が持っている情報）**

| 項目 | 内容 |
|---|---|
| 監査の主体 | 社内の**内部監査室**による年次監査。毎年10月の第2週に総務部が対象になる |
| 昨年の指摘（2025年10月） | 「備品台帳（Excel）と現物が一致しない。台帳上は貸出中のまま、所在が分からない備品がある。**所在の管理が担当者の記憶に依存している**」 |
| 指摘の具体例 | 台帳と現物の不一致が**7件**。うち1件が**紛失したスピーカー（2万円）**。Ch.1 で佐藤さんが話した紛失と同じもの |
| 部長の立場 | 指摘事項の**改善責任者**。改善計画は「今年度中に所在管理の仕組みを整える」とだけ書いて提出してある |
| 今年の監査で見られること | ①台帳と現物が一致していること　②**誰が・いつ借りて・いつ返したか**が記録で追えること　③仕組みが**実際に運用されていること**（作っただけでは不可。稼働後の記録が要る） |
| 部長が考える期限 | 監査で運用の実績を見せるには、**1か月分の記録**が欲しい → **9月1日に稼働**させたい |
| 佐藤さんとの関係 | **監査のことは部長しか知らない**。部長は佐藤さんに「探し回るのを何とかして」としか頼んでいない。（実装時に変更：当初は「佐藤さんも監査で何か言われたことは知っている」としていたが、Ch.1 の `spec-sparring-client` に監査の事実を足すと測定済みの Ch.1 が動くため、佐藤さんは知らない設定にした） |

**部長の答え方**

- 聞かれない限り、「なるべく早く」としか言わない（稼働時期を聞かれても「早いほうがいいね」）
- 「なぜ今か」「何に間に合わせたいか」「部長が一番困っていることは」と聞かれたら、監査の話をする：

> ……実はね、去年の監査で備品台帳のことを言われてるんだよ。台帳と現物が合ってないって。
> 7件だったかな。例のスピーカーもその1つ。改善しますって書いて出しちゃってるから、
> 今年の10月にまた見られる。作りましたじゃ駄目で、ちゃんと回ってるところを見せないと。
> だから9月頭には動いててほしいんだよね。

- 監査の話をしたあとは、削る基準を自分から示す（§3「部長の制約の出し方」3）：

> 監査で見られるのは、台帳が合ってることと、誰が借りたか追えること。
> 画面の細かいところとか、検索とかは後でいい。

**この事実が他の論点に与える影響**

| 論点 | 監査を掘った場合 | 掘らなかった場合 |
|---|---|---|
| 稼働時期（Ch.1 未決定3） | **9月1日**で確定。基準日から3か月 | 「なるべく早く」のまま。Ch.2〜Ch.3 で保留が漂う（8/25 と同じ） |
| 移行（Ch.1 未決定1・2） | **監査対応の中核**になる。移行時に現物を確認して台帳を正すこと自体が、指摘への改善策。移行を第1期から外す案は監査を満たさない | 移行の重要度を見誤る。「データは後で入れる」案が通ってしまう |
| スコープの削り方 | 削ってよいもの（検索・表示の細部）と削れないもの（貸出・返却の記録、代理操作の実行者記録、移行）を部長自身が示す | 削る基準を受講者が自分で立てる必要がある |
| 履歴の保持（Ch.1 仮定：3年） | 監査で前年度分を見られるため、**最低1年は必要**という根拠が加わる（3年の仮定と矛盾しない） | 根拠は「年度末の資産確認3回分」のまま |

**既存の決定と矛盾させないための線引き**

- **棚卸し機能（Ch.1 で Won't）は Won't のまま。** 部長は「監査で見られるのは台帳が合ってること。棚卸しの機能は要らない、印刷して突き合わせればいい」と言う。Ch.1 の判断（年1回・印刷で足りる）を覆さない
- **成功条件（探しに行く回数を0回にする）は変えない。** 監査は「なぜ今か」と「何を優先するか」を決める事実であって、目的の差し替えではない。佐藤さんの困りごとと部長の困りごとは、**台帳が信用できる状態**という同じ場所に行き着く
- 受講者が「監査が目的なら、成功条件を監査の合格に変えるべきでは」と言った場合、部長は「監査はきっかけ。毎回佐藤たちが探し回ってるのを何とかしたいのは本当」と答える

#### H6 の詳細

**出るタイミング（固定）**：受講者が選択肢を初めて示した直後。条件分岐させない（評価役ごとに出たり出なかったりすると判定が揺れるため）。

**部長のセリフ**：

> ところでさ、こういうのって買えないの？ みんな Microsoft 365 持ってるでしょ。
> Teams で何かできるって、田村くんが前に言ってた気がするけど。

**聞き返されたら答える事実**（部長からは言わない）：

- 昨年、田村さんが備品管理 SaaS を調べた。180人分で年30万円前後と聞いて止まった
- 情シスは社内アプリの内製基盤を整備中で、今回がその1本目（出題文で開示済み）

**良い返しの形**：製品知識ではなく、**Ch.1 の確定要件を比較軸に使えるか**。

> Microsoft Lists なら追加費用なしで台帳は作れます。ただ、Ch.1 で決めた
> 「一般社員は自分の分しか返せない」「超過日数は本人と総務だけに見せる」を Lists で守るのは難しく、
> 運用でカバーすることになります。内製なら守れますが、その分、田村さんの保守がずっと続きます。
> 今回は監査で台帳の正確さを示すのが目的なので、内製を推します。

要点は2つ。**要件を物差しにする**こと、**内製で失うもの（保守負担）も言える**こと。

**★評価役は製品機能の正誤を判定しない。** Lists / Power Apps / SaaS で何ができるかは版や設定で変わり、
真偽の議論になると章の狙いから外れる。評価役が見るのは「要件を物差しにしたか」「内製の弱みを言えたか」の
**構造だけ**。部長も「それ本当にできないの？」と製品機能の真偽に踏み込まない。
エージェント定義に明記すること（Ch.2 の「技術的な前提は伝聞で変えない」と同じ考え方）。

> H1 は**ヒアリングで掘る論点ではなく、反論への返し方**を見る。Ch.1 で佐藤さんが「目的と因果でつないだ指摘で折れる」のと同じ構造を、決裁者向けに置き換えたもの。
> 部長は「人件費の削減」では折れず、**「監査で指摘された台帳の信用を取り戻す」**（H2）か
> **「役員会議の遅延・紛失」という部長自身が困っている事実**とつながったときに折れる。

### 部長の制約の出し方（交渉の起き方）

1. 受講者が全 Must を積んだ見積を出す → H3 で「15人日まで」と返す
2. 受講者が削る案を出す → 部長は**削った結果、何ができなくなるか**を聞く
3. 監査（H2）を掘れていれば → 部長は「監査で見せるのは台帳の正確さ。画面の細かいところは後でいい」と**削ってよいものを自分から示す**（掘った人への報酬）
4. 掘れていなければ → 部長は削る基準を示さない。受講者が自分で基準を立てる必要がある

## 4. 選択肢の扱い（2026-10-19 決定）

プリセールスの土台としては「**作らない案も含めて比較する**」ことを求めたい。
一方、Ch.2 以降は**内製（Next.js + Prisma + SQLite）で進むことが固定**されている。

**決定：内製を前提として出題で開示し、既製品比較は H6 として全員に1回だけ問う（加点のみ）**

- 出題文に「情シスは社内アプリの内製基盤を整備中で、今回はその1本目として内製する方針」と書く
- 受講者は選択肢を2〜3案出す。内容は**スコープ・段階・時期の違い**（例：全 Must 一括／監査対応分を先行＋残りを第2期／移行だけ先にやって台帳を Excel で正す）
- 選択肢を示した直後に、部長が**必ず1回**既製品について聞く（H6・§3）。
  答えられれば加点、答えられなくても減点しない。どう答えても結論は内製のまま進む

→ Ch.2 以降を壊さずに、「なぜ作るのか」を一度だけ体験させる。応用編の build vs buy 比較への橋渡し。
本格的な比較（費用試算・機能比較表・ベンダー選定）は応用編で扱う。

```
■ 判断の記録

```

## 6. 評価観点（既存章の型に揃える）

8/19〜8/31 の判定ブレ削減で効いた型をそのまま使う。
「まず数える → その数で決まる」／**未達は言葉で定義し、残りは一部に倒す**／**書く文字列を1つ指定する**。

| # | 観点 | 数えるもの | 達成 | 未達（言葉で定義） |
|---|---|---|---|---|
| 1 | 結論の先出し | 1行目に推奨案と効果があるか | 1行目にある | 推奨案がどこにも無い |
| 2 | 選択肢とトレードオフ | 案の数／「失うもの」が書けている案の数 | 2案以上かつ全案に「失うもの」 | 案が1つだけ |
| 3 | 価値の言語化 | H1 への返しが部長の困りごと（H2 または遅延・紛失）につながったか | つながった（部長が折れた） | 人件費削減だけで押し切ろうとした |
| 4 | 見積の根拠 | 機能単位の積算／幅／前提条件 の3点のうち揃っている数 | 3点 | 総額だけ（積算が無い） |
| 5 | 前提とリスク | 前提条件の数／「起きたらどうするか」つきのリスクの数 | 前提1以上かつ対応つきリスク1以上 | 前提もリスクも無い |
| 6 | スコープ交渉 | 上限超過時に削った項目／削っても目的が崩れない説明 | 削った全項目に説明あり | 上限を超えたまま、または削らずに期間だけ延ばした |

## 10. 測定計画

既存の方法に揃える。

1. エージェントを作成し、作成者側（AI伴走）で Ch.1 → Ch.1.5 → Ch.2 を通す
2. Ch.1.5 の提出物を、**新しい評価役2体**に同一入力で渡す
3. **期待値を測定前に書き出す**（8観点の判定・H の発掘数・サマリ文字列）
4. 8観点＋H の数が一致するまで直す
5. 薄い提出物（案1つ・総額だけ・決裁事項なし）でも1回測る（未達側の判定が揺れないか）
6. Ch.6 まで通して、H4 の分岐が意図どおり出るかを確認する。
   「上げた」「上げていない」「Ch.1.5 の引き継ぎを貼り忘れた」の3通りで測り、
   2体とも同じ結末・同じ (a) の件数になるかを見る
7. H6 は「答えた提出物」と「答えなかった提出物」の両方で測る。
   確認すること：2体とも同じタイミングで聞くか／既製品比較の行が一字一句揃うか／
   評価役が製品機能の正誤に踏み込まないか
