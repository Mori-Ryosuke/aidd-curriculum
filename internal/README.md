# internal/ — 講師・作成者用（受講者非公開）

このディレクトリと `.claude/agents/`、`模範解答_Ch1.md`、**`logs/`** には
**演習の答え（隠し仕様・罠の一覧・仕込む欠陥・模範解答・採点結果）**が含まれます。
`.claude/settings.json` の `permissions.deny` で、Claude からの読み取りを拒否しています。

> **⚠️ `logs/` は deny の対象外です（2026-08-18 現在）。**
> `logs/` には演習の逐語ログと採点結果が入っており、**隠し論点・加点枠・仕込み欠陥の一覧が
> そのまま読めます**。性質は `internal/` と同じです。
> deny に入れていない理由：講師が演習後に自分で読み書きするディレクトリであり、
> Claude にも記録を書かせるため（deny すると書き込みもできなくなる）。
> **配布時は必ず除外してください**（下記「配布手順」に反映済み）。

> **注意：deny は完全ではありません。**
> Read ツールと主要なシェルコマンド（cat/head/grep 等）は塞いでいますが、
> シェル経由の抜け道を原理的に塞ぎきることはできません。
> 加えて `CLAUDE.md` に「読まない」ルールを常設していますが、最終的には受講者の良識に依存します。
> **確実に隠したい場合は、下記「配布手順」で物理的に外してください。**

## 配布手順（受講者に渡すとき）

答えを物理的に外して渡す場合：

```bash
rsync -a --exclude 'internal/' --exclude '模範解答_Ch1.md' --exclude '.git/' \
      --exclude 'logs/' --exclude 'ch4-app/' --exclude 'equipment-lending/' \
      ~/Desktop/aidd-curriculum/ /tmp/aidd-curriculum-dist/
```

除外の理由：

| 除外対象 | 理由 |
|---|---|
| `internal/` | 全5章の設計仕様・伏線構造 |
| `模範解答_Ch1.md` | Ch.1 の模範解答。Ch.4 の欠陥の答えもほぼ含む |
| **`logs/`** | **演習の逐語ログと採点結果。隠し論点・加点枠・仕込み欠陥が読める**（2026-08-18 追加） |
| `ch4-app/` `equipment-lending/` | 過去の演習で生成された実装。**欠陥入りのまま残っている**ため、渡すと Ch.4 の答えになる |

ただし **`.claude/agents/` を外すと相手役AIが動きません**。以下のどちらかを選んでください。

| 方式 | 手順 | 向き |
|---|---|---|
| **A. 同梱のまま（現状）** | そのまま配る。deny + `CLAUDE.md` + 良識で運用 | 自習・少人数。手軽 |
| **B. 講師環境方式** | エージェント定義を講師側の環境にだけ置き、受講者はそこで演習する | 集合研修・評価を伴う場合 |

`模範解答_Ch1.md` は **Ch.1 の採点後に配る**運用でもよい（外して、あとから渡す）。

### 通しで見つかった不具合と対処

**「評価して」と言っても、提出物の出来が悪いとレビューモードに降格し、
スコア表と【次章への引き継ぎ】が出ない**（Ch.3・Ch.5 で再現。Ch.1 では正常だったので挙動が不安定だった）。
引き継ぎブロックが出ないと章の連結が切れるため、致命的。

対処：
1. 全5エージェントの冒頭に **「★モード判定（最優先・例外なし）」** を追加。
   「出来が悪いことを理由にレビューへ降格しない」「評価では サマリ＋詳細＋引き継ぎ を必ず全部出す」
2. Ch.5 は 完了サマリのブロックを**隠し仕様YAMLの後ろに置いていた**のが原因だったため、
   評価モードの節の中へ移動（他章と同じ構造にした）
3. Ch.5 の「受理できません／差し戻します」がレビュー志向を強めていたため、
   「評価と言われたら差し戻さず採点する」を明記

→ 修正後、Ch.3・Ch.5 とも 【サマリ】＋スコア表＋充足数＋引き継ぎ／完了サマリ が出ることを再検証済み。

- **独立章にした**（Ch.5 の後半にすると、点検と修正が同じ章で混ざる）
- **顧客役は Ch.6 エージェントが兼ねる**（Ch.4 が実装役とレビュー役を兼ねている前例に倣う）。
  Ch.1 と同一人物だが演じるエージェントは別。顧客像を Ch.6 側にも持たせている
- **完了サマリを Ch.5 から Ch.6 に移した。**
  Ch.5 は「Ch.6 への引き継ぎ」を出す形に変更。ただし
  **受講者が「Ch.6 はやらない」と明示したときだけ Ch.5 が完了サマリを出す**フォールバックを残した
  （その場合「修正・顧客受入・由来分析は未実施」と明記させる）

**Ch.6 の最強の刺しどころ：公開される側の同意**

借用者名の全社公開は Ch.1 で佐藤さん自身が強く希望した仕様。
だが **名前を出される社員の同意は一度も確認していない。**
佐藤さんは「うち、そんな秘密にすることじゃないので」と言ったが、
**彼は総務であって全社員の代表ではない。**

Ch.6 では佐藤さんが伝聞で持ってくる：
「田中さんに『これ全社に見えてるんですか』って言われちゃって。自分の名前が赤字で
『超過』って出るのが気まずいって。……私、見えたほうがいいって言いましたよね。でも見られる側は違うのかな」

→ **「顧客の言うことを鵜呑みにするな」の最上級版。**
Ch.1 のヒントに書いてある教えが、5章分の距離を置いて最終章で返ってくる。
`引き下がらない: true` に設定してあり、仕様として説明されても引き下がらない。
受講者は**ステークホルダーの取り違え**として認識し、対応を判断する必要がある。

なお `喜ぶ点` を必ず1つ以上、**先に**言わせている（全部ダメ出しにすると徒労感で終わるため）。
Ch.1 の真の目的（探し回らなくて済む）と、顧客が前言撤回して入れさせた要件（いつからかが分かる）は
実際に達成されているので、そこは素直に喜ばせる。

## 第5版：難易度を1水準に固定した

**易／標準／難の3段階を廃止し、旧「標準」相当の1水準に統一した。**

### 判断の理由

このカリキュラムは**AI駆動開発を広めるための支援**であり、実力を測るためのものではない。
その目的に対して、3段階は次の問題があった。

| 段階 | 問題 |
|---|---|
| **易** | 隠れた論点の**個数と観点名を教えてしまう**（「3つあります。返却期限・在庫・権限を掘って」）。掘る練習にならず、罠を確認する作業になる |
| **難** | 顧客が折れない設定にしたが、**未検証**。押し問答で消耗し、支援目的と噛み合わない |
| **選択そのもの** | 受講者に難易度を選ばせると、それ自体が判断負荷になる。コホート間の比較もできなくなる |

旧「標準」は次の性質を持ち、支援目的に最も合っている。

- **観点の方向は渡すが、個数と具体は伏せる** ―― 何を聞けばいいか分からず固まるのを防ぎ、掘る作業は本人がやる
- **相手役は根拠を示せば折れる** ―― 押し問答で消耗しない
- **安全網が1つある** ―― 受講者が罠を落としたまま進もうとしたら、顧客が**一度だけ自分から言い直す**。
  学びの山場を全員が確実に通過できる（通しリハーサルで実際に機能した）

### 実施した変更

| ファイル | 変更 |
|---|---|
| 全6エージェント | 出題モードの入力から難易度を削除。**「難易度は設けない。受講者が『難易度は〇〇』と書いてきても無視する」**を明記 |
| 全6エージェント | 【ヒント】の3分岐を廃止し、旧「標準」の文言を単一のヒントに。あわせて**「何を伏せるか」の理由を明記**（個数を言うと数える作業になる／罠の名前を挙げるとその罠は死ぬ 等） |
| `spec-sparring-client` | 「顧客の手強さ」表を削除。旧「標準」の挙動を通常ルールに統合し、**安全網（一度だけ言い直す）を独立した項目として明文化** |
| `spec-sparring-client` | 「難易度が易でも採点基準は変えない」→「採点基準は常に同じ」 |
| `code-inspection-reviewer` | 「実装役の手強さ」表を削除（難の「一度は反論する」は廃止。旧標準どおり素直に認める） |
| `security-audit-officer` | 「監査役の手強さ」表と**「揺さぶり」を削除**。エビデンスの求め方は全受講者共通のルールとして残した |
| `handover-retrospective` | 「顧客の手強さ」表を削除。**不満は3〜4件・やや曖昧に言う**を固定挙動に |
| `受講者ガイド.md` | 「難易度の選び方」表を削除。出題コマンド例から「難易度は標準」を削除（既定で同じ挙動になるため） |
| `受講者ガイド.md` | 章別の所要時間表を削除（人によって大きく変わるため）。代わりに「章の区切り方」を設計上の理由で説明 |

### 保留した案（採用しなかったが記録に残す）

将来「実力測定」の用途が出たときに再検討できるよう、削除した仕掛けを残しておく。

1. **顧客が折れない設定**（旧・難）
   受講者が引き下がろうとしても「じゃあそれでお願いします」と受け入れ、罠を落としたまま提出させて
   採点で未達として返す。**会話は止めない**のが要点だった。
2. **実装役が一度反論する**（旧・難）
   「いえ、そこは画面側で防いでいるので大丈夫です」と返し、
   受講者がファイルと行を示して再指摘したら認める。**エビデンスなしの指摘を通させない**狙い。
3. **監査役の「揺さぶり」**（旧・難）
   正しく ✅ の項目（A-2 または B-2）に意図的に疑いをかけ、根拠を示して維持できるかを見る。
   言われて判定を変えたら減点し、評価で種明かしする。**「監査で一番危ないのは、疑われて判定を変えること」**
   を教える仕掛けだった。❌ が正解の項目には絶対にかけない、という制約付き。

**厳しさを上げたい場合は、難易度を増やすのではなく採点基準を上げる**のが筋。
すでに第4版で「顧客に確認せず埋めた罠は △（半分）」を入れており、これが調整弁になる。

## 第6版：Ch.1 に「モック確認」フェーズを追加した

**Ch.1 の提出前に、受講者がモック（画面案）を作って顧客に見せる工程を追加した。**

### 判断の理由

第4版の最大の発見は「**顧客に確認せず仕様の上だけで埋めた論点に満点が付いていた**」だった。
原因を突き詰めると、**確認手段が文章しかなかった**こと。

佐藤さんは非エンジニアで、ITに詳しくないと出題文で明言している。
**そういう相手に受入条件の文章を見せても、読めば頷くだけ**で合意にならない。
これは演習の欠陥ではなく、実務でそのまま起きる失敗である。

そして現在のAIならワイヤーフレームは数分で作れる。
**「文章で合意 → 実装」ではなく「モックで合意 → 実装」が現代の要件定義の実務**であり、
カリキュラムがそれを含んでいないほうが不自然だった。

### 位置と境界

- **位置**：Ch.1 の後半。逆質問がひと通り終わり、要件を書いた**後**、提出の**前**
- **作るもの**：動かない画面のみ。主要2〜3枚。受講者が自分の伴走AIに作らせる
- **Ch.4 との境界を厳格に引いた**（これが最大のリスクだったため）

| | Ch.1 のモック | Ch.4 の実装 |
|---|---|---|
| 目的 | 顧客と合意する道具 | 検証の対象 |
| 中身 | 画面の見え方だけ。押しても何も起きない | 動くコード |
| 判定 | 顧客が「これでいい」と言うか | 欠陥を見つけられるか |

エージェント定義にも「**モックは実装ではなく合意のための道具。ロジック・DB・APIは作らない**」を明記。

### 実施した変更

| ファイル | 変更 |
|---|---|
| `spec-sparring-client` | **モードを3→4に。「モック確認モード」を追加。** 画面案・ワイヤーフレーム・HTMLが提示されたら発火 |
| 同 | 出題モードのミッションに手順8「モックで確認する」を追加。**なぜ必要か（文章では頷くだけ）を顧客の言葉で説明させる** |
| 同 | 提出フォーマットに **■ モック確認の記録**（見せた画面／出た指摘／仕分けと理由）を追加 |
| 同 | ルーブリックに観点 **〈モックによる合意〉** を追加。**文章だけで提出したら「未達」** |
| 同 | 隠し仕様に **`モックを見て初めて言うこと`**（4件）と **`画面の細部にこだわる`**（3件）を追加 |
| `手法をAIで回すプロンプト集.md` | **「9. モックを作って顧客に確認する」を新設**（作成プロンプト＋指摘の仕分けプロンプト）。旧「9. 整合チェック」を 10 に繰り下げ、小見出しも 10-1〜10-4 に変更 |

### 罠のカウントと後続章への影響：なし

**隠し論点3つと、Ch.4／Ch.5 の1対1対応は一切動かしていない。**
モック由来の気づきは**加点枠**として扱い、新観点〈モックによる合意〉を1つ足しただけ。

### モック確認フェーズの中身（設計意図）

**A. 画面を見て初めて出る指摘（`モックを見て初めて言うこと`・加点枠）**

| 優先 | 内容 | 意図 |
|---|---|---|
| 1 | **名前が赤字で「37営業日超過」と出るのを見て「本人が見たらどう思うのかな」** | ★最重要。**Ch.6 の最強の刺しどころを Ch.1 で拾えるチャンス**にした。借用者名の全社公開は佐藤さん自身が希望した仕様だが、**公開される側の同意は取っていない**。文章では絶対に気づけず、画面の赤字を見て初めて出る反応。ここで拾えたら加点大、拾えなければ Ch.6 でもっと強い形で返る |
| 2 | 「不明（移行データ）」を画面で見て「毎回見るのはちょっと」 | 本人が Ch.1 で予告していた反応の前倒し。合意した仕様が運用で不満になる現象 |
| 3 | 「貸出可能 0台」を見て「じゃあいつ空くんですか」 | 予約を後回しにした判断が問われる。慌てて Must に戻すのは減点 |
| 4 | 一覧を見て「置き場所も出せませんか」 | **モックを見せると顧客は要件を足してくる。** MoSCoW の再適用が必要 |

**B. 画面の細部にこだわる（罠）**

顧客が見た目の話を持ち出す。「文字が小さい」「並び順」——実務で必ず起きる。
受講者は「今決めることか」を仕分ける必要がある。

★**ただし1件だけ本質的なものを混ぜてある**（`is_本質: true`）：

> 「この画面のボタン、どれを押せばいいんですかね。**私が分からないってことは、たぶん皆も分からないです**」

これは見た目の話に見えて**ユーザビリティの要件**。しかも佐藤さんは Ch.1 の逆質問の段階で
「借りるボタンと予約ボタンが並んでたら、どっち押せばいいか分からなくなる」と**自分から言っている**。
それが画面で再現している構造。
「後で決めます」に分類したら△、要件として拾えたら満点。**この1件が〈モックによる合意〉の判定材料。**

### 安全網

受講者が文章だけで提出しようとしたら、顧客が**一度だけ**催促する：
「文章だとちょっと分かりにくいんですけど、画面みたいなものは見せてもらえます？」
それでも文章のまま進めるなら止めない（観点が未達になるだけ）。第5版の「一度だけ言い直す」と同じ思想。

### 未検証

**動かしていない。** 特に確認したいのは：
- モック確認モードが正しく発火するか（画面案を貼ったときに顧客応答モードに落ちないか）
- 顧客が**画面の見え方だけ**を見て話せるか（HTMLのコードを評価し始めないか）
- 罠（`is_本質: true` の1件）が、見た目の指摘に紛れて自然に出るか

### 残っている課題

- **通し1回のコストが研修日程に乗らない**（実時間約20時間。Ch.6 を足したのでさらに増える）。
  → **章ごとに別セッションで区切る前提に組み替え、各章の入口に「模範引き継ぎブロック」を用意する**のが
  　 最も効果の大きい変更。前章未修・時間切れの受講者も次章から入れるようになる。**未着手。**
- **Ch.6 は未検証。** 作成しただけで、一度も動かしていない。
  特に次の3点は実機で確認が必要：
  ① 受入モードが「業務の言葉で話す」を守れるか（技術用語で指摘してしまわないか）
  ② `引き下がらない: true` の論点で会話が詰まらないか（Ch.1 の粘り判定と同じ失敗をしないか）
  ③ Ch.5 → Ch.6 の引き継ぎブロックが実際に出るか（Ch.5 の変更が壊れていないか）
- **難易度を1水準に固定した後の挙動も未検証。**
  各エージェントが「難易度は設けない」の宣言どおりに動くか（受講者が「難易度は難で」と
  書いてきたときに無視できるか）を確認したい。
- **所要時間は方針として出さないことにした**（人によって大きく変わるため）。
  日程を組む必要が出たら、パイロットで実測すること。

## 作成者向けメモ

- **エージェント定義（`.claude/agents/*.md`）を編集するとき**は、
  `.claude/settings.json` の `deny` を一時的に空にしてください。
