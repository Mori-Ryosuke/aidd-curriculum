AIDD 要件定義カリキュラム Ch.1 ／ レビュー指摘への対応報告

ユビキタス言語・EARS を追加したことによる効果

題材：review-feature（商品レビュー機能・難易度 標準）

レビューでご指摘いただいた「ユビキタス言語」「EARS記法」の2手法を、演習・プロンプト集・採点ルーブリックの3箇所に追加しました。追加後に通しで演習を実施し、追加前の設計と比較しています。

結論として、この2つは「受講者の成果物を良くする」効果より、「受講者の弱点が採点者から見えるようになる」効果の方が大きいという結果になりました。以下、根拠を示します。

1. 結論（3点）

  1. ユビキタス言語は「最も手戻りの大きい種類のミス」を演習の中で顕在化させた。「レビュー」に星評価を含むかという解釈のズレが演習中に実際に発生し、受講者が自力で気づいて潰した。この1問を実装後に発見すると、影響はDB・集計・UI・API・テストの5領域に及ぶ。
  2. EARSは採点の解像度を上げた。追加前の6観点では「AC網羅性：達成」で終わっていた提出物から、丸め規則の未定義・ソートキーの曖昧さ・境界ACの欠落という3件の具体的な穴を名指しで指摘できるようになった。
  3. 2手法の追加が、さらに1つの観点（仮定の明示と整合）の必要性を露呈させた。EARSで要件を書き切ると「決めた仮定」が本文に溶け込むため、未確認リストとの二重帳簿が起きる。副産物として採点観点をもう1つ追加した。

2. 何を追加したか

資材追加内容
手法をAIで回すプロンプト集 「2. ユビキタス言語」「6. EARS記法」の2節を追加（全6節→8節）。EARSは5つの型（常時／WHEN／WHILE／IF-THEN／WHERE）の説明つき
演習エージェント
（出題の進め方）		 進め方を5ステップ→7ステップに。①逆質問 → ②ユビキタス言語 → ③INVEST → ④MoSCoW → ⑤非機能 → ⑥EARS → ⑦AC
採点ルーブリック 「用語の統一（ユビキタス言語）」「要件の明確さ（EARS）」の2観点を追加。あわせて隠し論点の数え方を厳格化（触れただけは△＝半分）
受講者ガイド 手法一覧・模範解答を2手法に対応させて更新

設計上の位置づけ：2手法は既存手法の間に挟まる形で、それぞれ別の穴を塞いでいます。ユビキタス言語は逆質問 → INVEST の間（＝ストーリーを書き始める前に語彙を揃える）、EARSは 非機能 → AC の間（＝Given-When-Thenに落とす前に曖昧語を排す）。順序に意味があるため、この位置に固定しています。

3. 効果①：ユビキタス言語 — 最も高くつくミスを演習内で顕在化させた

演習の中で実際に起きたこと

顧客役（EC事業部PM・田中さん）の初期要望は「商品ページにレビュー機能つけたい。いい感じにお願い」。この時点で、受講者と顧客は「レビュー」という語を違う意味で使っていました。

受講者の理解

レビュー ＝ 文章（感想）

テキストの投稿・表示ができればよい

顧客の頭の中

レビュー ＝ ★がピカピカ付いていて文章もある、あの感じ

「他社のがそうだから」以上の言語化はされていない

受講者は表示の並び順を検討する過程で「評価の高い順」という言葉を自分で使い、そこに星が前提されていることに自分で気づいて顧客に確認しました。顧客の回答は「あー、そこか。正直あんまり区別してなかったわ」。

この1問の価値（＝実装後に発見した場合の影響範囲）

領域星を後から足す場合に発生する変更
データレビューテーブルに評価列を追加。既存レビューの値をどうするか（NULL許容／一律値）の判断が必要
集計平均評価・件数の保持と再計算。非表示レビューを母数から外す処理
画面（閲覧）一覧の星表示、商品ページ上部の平均評価サマリ
画面（投稿）星の入力UI、必須バリデーション
機能「評価の高い順」の並び替え（星がなければ実装不能）
API・テストレスポンス契約の変更、既存テストの改修

要件定義の段階なら「星は付きますか？」という一問で済み、所要は数十秒です。この非対称性こそが、ユビキタス言語を独立した工程として置く理由であり、演習で体験させたい山場でした。

追加前の設計では、ここは採点対象になっていなかった

「用語のズレ」は元々、隠し仕様に仕込まれてはいました。しかし採点ルーブリックには対応する観点がなく、掘り当てても掘り漏らしても点差になりませんでした。今回2観点を追加したことで、はじめて「用語を定義したか」を評価できるようになっています。

4. 効果②：EARS — 採点の解像度が上がった

受講者の成果物への効果

提出物の中で、曖昧な日本語が検証可能な条件に置き換わりました。特に IF ... THEN の型が異常系の抜けを可視化しています。

EARS導入前によくある書き方
・大量のレビューがあっても
  遅くならないこと
・不適切な投稿は
  良しなに対応できること
・エラー時は適切に処理する

「遅くない」「良しなに」「適切に」＝ 実装者が各自の解釈で決めることになる

EARS導入後（今回の提出物より）
WHEN 訪問者が商品ページを開いたとき、
  システムは公開中レビューを投稿日時の
  降順に最大20件表示すること

IF レビュー取得に失敗した場合、THEN
  システムは商品情報とカート導線を通常
  表示し、レビュー欄のみエラー表示すること

WHILE 公開中レビューが0件である間、
  システムは「まだレビューがありません」
  を表示し、平均評価を表示しないこと

提出物には IF-THEN 型の要件が8本含まれていました。うち「レビュー取得に失敗しても商品ページ本体とカートボタンは生きている」という縮退要件は、顧客との会話には一度も出てこなかった論点です。型に当てはめる過程で受講者が自力で追加しました。

採点への効果 — ここが最も大きい

EARS観点を追加した結果、従来なら「AC網羅性：達成」で流れていた提出物から、3件の具体的な欠陥を名指しで指摘できました。いずれも「網羅性」というくくりでは表現できない、粒度の細かい曖昧さです。

指摘内容放置した場合に起きること
平均評価の丸め規則が未定義 「小数第1位まで表示」としか書かれておらず、4.25 が 4.2 か 4.3 か決まっていない 実装者が独自判断 → 後から「四捨五入だと思っていた」で修正。表示される評価点は争いになりやすい
「新着順」のソートキーが不明 投稿日時か更新日時か未定義。レビューは書き直せる仕様になっている 更新で先頭に浮上する実装になると、書き直しを繰り返して自分のレビューを上位固定できる（1人1件の制限が抜け道で無効化）
自分で決めた閾値の境界ACがない 「1000文字を超えたら拒否」と書いたのに、AC に 1000／1001 のケースがない off-by-one の温床。AC19本のうち、この1件だけが抜けていた

3件とも 「EARSで書いた要件」と「AC」を突き合わせて初めて見つかる種類の穴です。EARS観点がなければ、この提出物は全観点「達成」で終わっていた可能性が高い。受講者にとっては「合格したのに次に何を伸ばせばいいか分からない」状態が、「この3点を直せ」に変わりました。

5. 提出物に現れた変化

数値の読み方について。同一受講者・同一題材での追加前後の対照は取っていないため、「AC本数が増えた」等の数値は、手法の効果と受講者の力量を分離できていません。

一方で、「EARS観点があったから3件の指摘が出せた」という事実は、観点の有無に直接起因します。指摘3件はいずれも、旧6観点のどこにも対応する記述枠がありません。

6. 副次効果：さらに1観点の必要性が見つかった

2手法を入れて実走したことで、想定していなかった問題が表面化しました。

EARSで要件を書き切ると、「顧客に確認できていないので仮に決めた値」が本文に溶け込みます。たとえば「本文が1000文字を超える場合は拒否する」と書いた時点で、1000という数字は仕様として確定して見える。ところが受講者は末尾の未確認事項リストにも「文字数上限は未確認」と書いていました。同じ項目が二箇所に、違うステータスで存在する状態です。実装者はどちらを信じればいいか分かりません。

問題（二重帳簿）
本文：IF 本文が1000文字を超える場合、
     THEN 投稿を拒否すること

未確認事項：
  ・文字数上限（未確認）
改善後（Q番号で参照）
本文：IF 本文が1000文字を超える場合、
     THEN 投稿を拒否すること［仮置き:Q1］

未確認事項：
  Q1 文字数上限＝1000字で仮置き
     → 顧客（委任済み・事後承認）

そこで採点ルーブリックに「仮定の明示と整合」を追加しました（①仮定を明記したか ②仮定と本文が矛盾していないか ③誰に確認すべきかが書かれているか）。顧客役は「そっちで決めて『こうしました』って書いといて」と委任してくる挙動を持っているため、採点材料は毎回安定して発生します。

これは2手法を追加しなければ表面化しなかった問題です。指摘いただいた2手法が、カリキュラム全体の精度を一段上げたと考えています。

総括：2手法の追加は妥当だったと考えています。

特にEARSは、受講者の成果物を良くする以上に「採点者が受講者の弱点を具体的に指摘できるようになる」効果が大きく、演習カリキュラムとしての価値が上がりました。ユビキタス言語は、実装後に発見すると最も高くつく種類のミス（用語の解釈違い）を、演習の中で体験させる装置として機能しています。
